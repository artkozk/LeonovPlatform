# Рабочий фокус, быстрые карточки и задача из решения

Дата: 13 августа 2026 года.

Документ описывает актуальное поведение платформы после редизайна рабочего обзора и оптимизации открытия карточки. Предыдущие продуктовые документы остаются историей решений и не заменяются этим файлом.

## Причина изменений

Предыдущий обзор технически показывал нужные данные, но почти все элементы имели одинаковый белый фон, одинаковый визуальный вес и занимали много горизонтального пространства. Пользователю приходилось самостоятельно искать следующую задачу среди метрик, быстрых действий и списков. Это создавало ощущение набора полей, а не рабочего инструмента.

Открытие карточки ожидало завершения полного `GET /api/records/{id}` до показа диалога. Сервер последовательно читал основную запись, разделы, связи, оценки, доказательства и специализированный процесс вопросов. Дополнительно middleware записывал `last_seen_at` в SQLite на каждом API-запросе. При единственном соединении с SQLite эти операции создавали очередь даже для данных, которые пользователь ещё не собирался смотреть.

## Как работает обзор сейчас

1. Верхний блок показывает состояние проекта и количество активных карточек, но не конкурирует с рабочей задачей.
2. Блок «Фокус на сегодня» выбирает до четырёх личных активных задач. Сортировка сначала учитывает просрочку и срочность, затем срок.
3. Первая задача получает усиленное представление со сроком и прогрессом. Остальные задачи остаются компактными строками в том же блоке.
4. Быстрые действия разделены по смыслу и цвету: идея, общая задача и карточка вопросов. Кнопка «Общая задача» доступна прямо на обзоре и открывает обычное создание задачи с выбором ответственного.
5. Метрики используют разные сигнальные цвета: синий для работы, красный или коралловый для контроля срока, бирюзовый для обсуждений и янтарный для идей.
6. Загрузка команды, ближайшие сроки и история сохранены ниже основного фокуса. Они поддерживают контроль, но не отвлекают от следующего действия.

Такое расположение выбрано для ежедневного использования двумя основателями. Первый экран отвечает на вопрос «что делать сейчас», а не только перечисляет накопленные сущности.

## Новый путь открытия карточки

После клика выполняются следующие шаги:

1. Клиент немедленно открывает `dialog`.
2. Если карточка ещё не загружалась, диалог показывает название из общего списка и скелетон основной формы. Пользователь сразу получает обратную связь о клике.
3. Если карточка уже есть в кэше и её `updatedAt` совпадает с записью общего списка, форма появляется без ожидания сети.
4. При наведении или фокусе на строке карточки клиент запускает безопасную предварительную загрузку. Одновременные запросы к одной карточке объединяются через `detailRequests`.
5. При фоновом обновлении карточки используется идентификатор активного запроса. Ответ ранее открытой карточки не может заменить более новую карточку, которую пользователь открыл следом.
6. После обновления общего списка кэш удаляется только для исчезнувших карточек и карточек с изменившимся `updatedAt`.
7. При ошибке вместо пустого или зависшего окна показывается понятное состояние с кнопкой повторной загрузки.

Кэш не является источником истины. Источником истины остаётся сервер и SQLite; кэш только сокращает повторное ожидание и инвалидируется после мутаций.

## Разделение серверного ответа

`GET /api/records/{id}` теперь возвращает только данные, нужные для первого полезного экрана:

- основную запись;
- раскрывающиеся разделы для обычной карточки;
- доказательства только для задачи;
- вопросы, ответы и совместные итоги только для карточки вопросов;
- пустые `links` и `scores` с флагом `relationsLoaded: false`.

`GET /api/records/{id}/relations` отдельно возвращает связи и оценки. Клиент вызывает его при первом открытии вкладки «Связи и оценка». После успешного ответа флаг меняется на `true`, а счётчик вкладки показывает фактическое число связей.

Разделение сделано по пользовательскому сценарию: для чтения названия, срока, исполнителя, описания или доказательств связи не нужны. При этом функциональность связей не урезана и остаётся доступной в один клик.

Каждый из двух endpoint добавляет `Server-Timing`:

- `record-detail` для основной карточки;
- `record-relations` для связей и оценок.

Это позволяет отличать сетевое ожидание от времени серверной обработки при следующих оптимизациях.

## Снижение конкуренции SQLite

Проверка сессии по-прежнему выполняется при каждом защищённом запросе. Запись `sessions.last_seen_at` теперь выполняется не чаще одного раза в пять минут для конкретной сессии. Раньше обновление происходило на каждом запросе, включая пять параллельных запросов начальной загрузки.

Пятиминутный интервал не меняет срок действия сессии и не ослабляет аутентификацию. Он только убирает технические записи, не несущие полезного аудита для пользователя.

## Задача из совместного решения

После того как по вопросу зафиксирован совместный итог, рядом с итогом появляется команда «Создать задачу».

1. Название новой задачи формируется как `Реализовать решение: <текст вопроса>` и ограничивается длиной поля карточки.
2. В описание автоматически переносятся исходный вопрос и совместное решение.
3. Пользователь выбирает исполнителя, срок и оценку времени в стандартной форме задачи.
4. После создания сервер добавляет связь от карточки вопросов к задаче с типом `leads_to`.
5. В истории создания связи сохраняется причина `Задача создана из совместного решения`.
6. Открывается одна созданная задача; копирование карточки вопросов или ручной перенос текста не требуется.

Создание карточки и добавление связи выполняются двумя API-запросами. Если второй запрос оборвался, интерфейс не оставляет форму создания открытой и не провоцирует повторное создание дубликата: уже созданная задача открывается, а отдельное сообщение сообщает, что связь нужно добавить вручную. Атомарный серверный endpoint для обеих операций остаётся возможным усилением после стабилизации модели процессов.

Теперь первый рабочий процесс продолжается как `карточка вопросов → вопрос → ответы основателей → совместное решение → задача`. В будущей версии к задаче можно будет присоединить результат и отдельную карточку решения, но текущая цепочка уже пригодна для работы.

## Мобильное поведение

На ширине до 820 пикселей рабочий фокус и быстрые действия переходят в одну колонку. На ширине до 560 пикселей:

- заголовок проекта переносится без изменения размера шрифта от ширины экрана;
- название фокусной задачи переносится на несколько строк и не обрезается;
- четыре метрики располагаются сеткой два на два;
- диалог карточки занимает доступную ширину, вкладки прокручиваются горизонтально;
- боковая колонка фактов скрывается, потому что те же поля уже доступны в основной форме.

## Проверки релиза

Локально выполнены:

```powershell
go test ./...
go vet ./...
node --check web/app.js
git diff --check -- business-control
```

Интеграционный тест дополнительно подтверждает:

1. основной ответ карточки не содержит заранее загруженных связей и оценок;
2. endpoint связей возвращает созданную связь и оценку;
3. оба ответа содержат соответствующий `Server-Timing`;
4. задача, созданная из решения, обнаруживается в связях карточки вопросов с типом `leads_to`;
5. прежние сценарии статусов, доказательств, уведомлений и совместных ответов не регрессировали.

В браузере проверены обзор с активной задачей, открытие задачи после холодной перезагрузки, вкладка связей и мобильный экран 390 × 844. При инструментальном клике диалог появился за 287 мс вместе с накладными расходами удалённого управления браузером; к моменту снимка основная форма уже была доступна.

## Оставшиеся ограничения

- Общий список карточек и история по-прежнему загружаются целиком. При сотнях или тысячах записей понадобятся серверная пагинация и виртуализация списка.
- Предварительная загрузка работает только после наведения или фокуса; на сенсорном экране пользователь увидит скелетон до ответа сервера.
- Автоматическая связь создаётся с карточкой вопросов целиком, а не с отдельной сущностью вопроса. Это соответствует текущей модели, где вопросы принадлежат одной групповой карточке.
- SQLite остаётся оправданным для двух основателей, но увеличение числа одновременных пользователей потребует повторного измерения очереди запросов и, вероятно, перехода на PostgreSQL.
