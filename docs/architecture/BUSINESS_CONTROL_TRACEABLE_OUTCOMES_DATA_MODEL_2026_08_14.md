# Business Control: модель происхождения результатов и встреч

Дата: 14 августа 2026 года.

## 1. Причина изменения схемы

Обычной many-to-many связи недостаточно для ответа на вопрос «как именно мы пришли к этой карточке». Связь с группой вопросов не указывает конкретный вопрос и конкретный совместный итог. Кроме того, редактирование исходного решения не должно переписывать историческое основание уже созданного правила.

Миграция `003_traceable_outputs_and_meetings.sql` добавляет классификацию записей и отдельную таблицу происхождения.

## 2. Поле `records.record_kind`

Поле хранит предметный подтип поверх существующего технического типа:

- пустая строка — обычная карточка старого формата;
- `preference` — положительный критерий;
- `limitation` — ограничение;
- `rule` — постоянное правило;
- `insight` — самостоятельный вывод;
- `meeting` — встреча, физически хранящаяся как `document` ради совместимости базового ограничения типов.

API возвращает встречу как виртуальный тип `meeting`. Поэтому frontend не знает о внутреннем типе `document`, а старый бинарник способен читать базу после добавления новых столбцов.

## 3. Таблица `record_derivations`

Каждая строка описывает происхождение одной выходной карточки:

- `output_record_id` — созданная карточка; уникальна в таблице;
- `source_record_id` — карточка-группа вопросов;
- `source_question_id` — конкретный вопрос;
- `source_decision_id` — конкретная запись совместного итога;
- `source_excerpt` — неизменяемый снимок текста итога;
- `created_by` и `created_at` — автор и время преобразования.

Все внешние ключи используют `ON DELETE RESTRICT`. Это согласуется с правилом продукта: карточки и основания не удаляются бесследно.

`source_excerpt` намеренно дублирует текст решения. Нормализация здесь нанесла бы вред аудиту: после обновления `question_decisions.content` прошлое происхождение стало бы показывать новый текст.

## 4. Транзакция создания результата

Endpoint `POST /api/records/{recordId}/questions/{questionId}/outputs` выполняет в одной транзакции:

1. проверку доступа и типа исходной карточки;
2. проверку существования активного вопроса;
3. проверку принятого совместного итога;
4. создание выходной записи с предметным `record_kind`;
5. создание связи `produced`;
6. создание `record_derivations` со снимком решения;
7. обновление времени исходной карточки;
8. две записи аудита: у источника и у результата;
9. commit.

Если любой шаг завершается ошибкой, не остаётся карточки без связи или происхождения.

## 5. Загрузка карточки

Первичный endpoint карточки загружает происхождение одним запросом с соединением исходной записи и вопроса. Текст решения берётся из `record_derivations.source_excerpt`, а не из текущего `question_decisions.content`.

Список связей и оценки по критериям остаются ленивыми и запрашиваются только при открытии вкладки `Связи`. Добавление происхождения не возвращает прежнюю задержку открытия карточки.

## 6. Встречи

Встреча хранится в общей таблице `records` с `type=document` и `record_kind=meeting`. При чтении API преобразует эту комбинацию в `type=meeting`. Запрос списка документов исключает встречи, запрос списка встреч выбирает только этот `record_kind`.

Такой подход сохраняет одну модель карточек, единые связи, историю, архивирование и настройки доступа. Отдельная таблица встреч сейчас не нужна, потому что у MVP нет списка участников, протокола реплик или повторяемости.

## 7. Совместимость и rollback

Миграция только добавляет столбец, индексы и таблицу. Старые строки получают пустой `record_kind`. Старый бинарник игнорирует новые данные схемы и продолжает читать известные поля.

Перед production-запуском обязательна копия SQLite. Откат приложения возможен переключением symlink на предыдущий release. Полный откат данных выполняется восстановлением копии только при подтверждённой проблеме целостности; обычный rollback бинарника не требует удаления миграции.

## 8. Автоматические проверки

Интеграционный тест проверяет:

- создание правила из совместного решения;
- тип `decision` и подтип `rule`;
- связь с группой и конкретным вопросом;
- наличие результата в workflow вопроса;
- неизменность `source_excerpt` после редактирования совместного итога;
- создание и чтение виртуального типа `meeting`;
- сохранение обычных связей с задачей.

Frontend-тест проверяет наличие объектно-ориентированного визуального слоя и встроенного шрифта. Синтаксис JavaScript, Go-тесты и `go vet` выполняются перед сборкой.
