# Архитектура Business Control MVP

Дата фиксации: 2026-08-12.

## 1. Назначение и граница системы

Business Control — принципиально новая независимая программа для двух партнёров, которые уже строят бизнес и должны фиксировать рабочую информацию во время разработки самой программы.

Она разворачивается отдельным процессом, использует отдельную SQLite и отдельный порт. Код находится в `business-control`. Изменения этого MVP не требуют правок существующих `backend` и `frontend` Leonov Care. Такая изоляция нужна, чтобы бизнес-система не зависела от учебного продукта, его миграций, очередей, платежей и релизного цикла.

## 2. Обязательные продуктовые инварианты

### 2.1. Одна карточка существует в одном экземпляре

Карточка хранится одной строкой в `records`. Разделы интерфейса и списки по статусам — запросы и фильтры над этой строкой.

Пример перехода идеи:

```text
inbox -> review -> main
                 -> rejected
```

При переходе меняется только `records.status`; `records.id` остаётся прежним. Разделы, связи, оценки и история продолжают ссылаться на тот же идентификатор. Это исключает ручное копирование и расхождение версий одной идеи.

### 2.2. Мысль сначала фиксируется, потом оценивается

Новая идея получает статус `inbox`. Система не требует оценки, аргументации или выбора цели во время создания. Это сохраняет сырые и потенциально бесполезные мысли без раннего решения о качестве.

### 2.3. Физического удаления доменных данных нет

Для карточек API предоставляет архивацию с обязательной причиной. Endpoint `DELETE /api/records/{id}` отсутствует. Связь не удаляется физически: `record_links.active` переключается в `0`, а журнал фиксирует автора и причину.

Определение универсального раздела можно отключить, но его строка и уже заполненные `record_sections` сохраняются. Это сделано для восстановления прошлого состояния проекта.

### 2.4. Важные изменения объяснимы

Изменение статуса или срока требует `reason`. В `activity.details_json` сохраняются значения `before` и `after`. Для разделов сохраняется предыдущее и новое содержание. Журнал append-only на уровне приложения: публичного API редактирования и удаления событий нет.

### 2.5. Задача не завершается без отчёта

Завершить задачу может назначенный ответственный. До завершения в `task_proofs` должна существовать минимум одна запись. Доказательство является отчётом исполнителя и намеренно не проходит approval в MVP: ответственность за качество приложенного материала остаётся у исполнителя, как указано в продуктовых требованиях.

## 3. Компоненты

```text
Browser
  -> embedded HTML/CSS/JavaScript
  -> same-origin JSON API
  -> Go net/http server
  -> database/sql
  -> SQLite file + WAL
```

Один бинарник обслуживает UI и API. Same-origin схема упрощает cookies и не требует CORS. SQLite-драйвер `modernc.org/sqlite` не требует CGO, поэтому production-бинарник можно собрать на Windows для Linux через `GOOS=linux GOARCH=amd64`.

## 4. Модель данных

### 4.1. Пользователи и сессии

- `users`: email, изменяемый unique login, bcrypt password hash, даты.
- `sessions`: SHA-256 hash случайного токена, срок жизни, время последнего использования.

В cookie хранится только исходный случайный токен. В БД хранится его hash, поэтому чтение БД не раскрывает активные токены напрямую. Cookie имеет `HttpOnly`, `SameSite=Lax`; `Secure` включается через env после настройки HTTPS.

### 4.2. Универсальные карточки

`records.type` принимает:

- `goal`;
- `task`;
- `idea`;
- `criterion`;
- `research`;
- `decision`;
- `disagreement`;
- `document`.

Общие поля: название, описание, статус, автор, ответственный, принимающий решение, срок, оценка времени, прогресс, текущая заметка, результат и даты жизненного цикла.

Общие поля нужны не для превращения продукта в таблицу, а для одинакового поиска, связей, Timeline и аудита. Типовые различия выражаются допустимыми статусами и разделами карточки.

### 4.3. Разворачиваемые разделы

- `section_definitions` задаёт универсальные и шаблонные пункты для одного типа или всех типов.
- `record_sections` хранит конкретное содержание карточки.
- `definition_id = NULL` означает добавленный вручную плавающий раздел конкретной карточки.

Начальная миграция создаёт пункты идеи: цели, критерии отбора, дополнительные параметры, аргументы, ограничения, исследования, вопросы без ответа, связанные записи и решения. Дополнительно создаются основные пункты для целей, задач, решений и разногласий.

### 4.4. Связи и критерии

`record_links` — направленная запись связи, которая показывается с обеих сторон. Одна карточка может иметь любое число связей с карточками любого типа. `relation_type` хранит смысл связи, например `related`, `supports`, `depends_on`, `result_of`.

`criterion_scores` связывает оцениваемую карточку с карточкой типа `criterion`. Оценка от 0 до 10 и пояснение хранятся отдельно, поэтому критерий можно переиспользовать для многих идей и направлений.

### 4.5. Уведомления и история

`notifications` хранит личные уведомления, признак прочтения и ссылку на карточку. При завершении задачи исполнитель может одним флагом уведомить всех остальных зарегистрированных участников.

`activity` хранит actor, entity type/id, action, JSON details, reason и timestamp. История и Timeline — два представления одного журнала: первое показывает аудит изменений, второе объединяет события с датами карточек.

## 5. Status machine

Идеи:

- `inbox` — зафиксирована без оценки;
- `review` — находится на рассмотрении;
- `main` — выбрана как главная;
- `rejected` — не подходит, но сохранена;
- `archived` — выведена из активной работы с причиной.

Цели и задачи:

- `planned`;
- `in_progress`;
- `blocked`;
- `completed`;
- `postponed`;
- `cancelled`;
- `archived`.

Остальные карточки:

- `draft`;
- `in_progress`;
- `completed`;
- `cancelled`;
- `archived`.

Backend проверяет допустимость статуса по типу. Для task запрещено обычное обновление в `completed`: используется отдельная транзакция завершения с проверкой proof.

## 6. Сроки и прогресс

Срок хранится в UTC в RFC3339. Браузер показывает локальное время пользователя. Цвет вычисляется клиентом относительно текущего времени:

- больше трёх суток — синий нейтральный;
- до трёх суток — янтарный;
- до суток — красный срочный;
- срок прошёл и задача не выполнена — красный просроченный;
- выполнено — зелёный.

Просрочка не является отдельным сохранённым статусом. Это вычисляемое состояние из `due_at` и `status`, поэтому оно возникает автоматически и одинаково отображается обоим партнёрам.

## 7. API первого релиза

Основные группы:

- `/api/auth/*` — регистрация, вход, выход;
- `/api/me`, `/api/users` — текущий профиль и команда;
- `/api/records*` — карточки, разделы, связи, критерии, proofs, завершение и уведомление;
- `/api/section-definitions*` — настройка универсальной структуры;
- `/api/notifications*` — личный кабинет уведомлений;
- `/api/activity` — аудит и Timeline;
- `/api/health` — health check с проверкой БД.

Тело запроса ограничено 1 MiB. SQL выполняется параметризованными запросами. Пароли хешируются bcrypt. Сервер задаёт CSP, `nosniff`, запрет iframe и same-origin referrer policy.

## 8. Согласованность и транзакции

Изменение доменного объекта и запись истории выполняются в одной SQL-транзакции. Завершение задачи, запись события и создание уведомлений также составляют одну транзакцию. Если аудит или уведомление не записались, основное изменение не коммитится.

SQLite работает с foreign keys, `busy_timeout=5000`, WAL и одним соединением записи. Для текущих двух пользователей это делает поведение простым и предсказуемым.

## 9. Что сознательно не включено

- подтверждение email и восстановление пароля;
- роли, сложные permissions и администрирование команды;
- бинарные вложения;
- внешние push/email/Telegram уведомления;
- realtime WebSocket;
- полноценные комментарии и упоминания;
- импорт из Excel;
- автоматическая аналитика качества идей.

Причина ограничения: продукт уже нужен для текущего бизнеса, поэтому первая версия закрывает фиксацию, совместные задачи, доказательства, связи и восстановимую историю. Следующая функция должна добавляться только по фактической рабочей боли, чтобы разработка платформы не стала основным бизнесом.

## 10. Путь дальнейшего развития

1. Накопить реальные карточки и задачи в MVP.
2. Через практическое использование определить 2–3 наиболее частых узких места.
3. Добавить вложения или обсуждения только при подтверждённой потребности.
4. Перед расширением команды добавить invitations, роли и password recovery.
5. Перед горизонтальным масштабированием перенести repository слой на PostgreSQL.

Исторические разделы этого документа не удаляются при пересмотре. Новое фактическое поведение добавляется отдельной датированной актуализацией с объяснением причины.

## 11. Актуализация 2026-08-13: специализированный процесс вопросов

Миграция `002_question_workflow.sql` расширяет модель без замены базового объекта `records`. Логический тип `question_set` хранится как `records.type=document` и `records.subtype=question_set`, поскольку исходное SQLite-ограничение `records.type CHECK(...)` нельзя безопасно расширить простым `ALTER TABLE` на рабочей базе. API скрывает эту деталь и в списках, карточках, связях, уведомлениях и аудите возвращает `type=question_set`.

Дочерние сущности нормализованы в `question_items`, `question_answers`, `question_decisions`. Уникальность `(question_id, author_id)` гарантирует один актуальный личный ответ пользователя, а `question_decisions.question_id UNIQUE` — один актуальный совместный итог. Все изменения дополнительно попадают в append-only `activity`, поэтому перезапись актуальной проекции не удаляет историю.

SQLite по-прежнему работает с `SetMaxOpenConns(1)`. Загрузка workflow сначала полностью читает и закрывает набор вопросов, а затем отдельными запросами загружает ответы и решения. Это необходимо, чтобы не ждать второе соединение при открытом `rows` и не создавать дедлок на одном соединении.

Статус карточки вопросов рассчитывается сервером в той же транзакции, что изменение вопроса. `planned -> in_progress -> completed` следует из количества активных и решённых вопросов. Добавление вопроса после завершения возвращает карточку в работу. Терминальные состояния всей карточки не перезаписываются вычислением.
