# Support Chat Implementation Blueprint (2026-05-16)

## 1. Цель

Подготовить безопасную спецификацию внедрения встроенной поддержки (ученик <-> админ) без деградации текущих production-сценариев обучения, проверки задач, биллинга и авторизации.

Документ фиксирует:

1. Что именно нужно реализовать.
2. Какие ограничения уже есть в проекте.
3. Как внедрять по шагам, чтобы не сломать сайт/backend.
4. Какие проверки обязательны до релиза.

## 2. Входные требования продукта

1. У каждого ученика есть кнопка `Поддержка`.
2. У ученика один общий диалог поддержки (не тикетная очередь из нескольких чатов).
3. У админа интерфейс как в Telegram:
- список чатов;
- последнее сообщение;
- время;
- непрочитанные.
4. Нужен realtime.
5. Вложения с обеих сторон:
- фото и другие медиа/файлы;
- не более 5 файлов в одном сообщении.
6. Нужны статусы сообщений «как в ТГ» (галочки).
7. Админка отдельной роли (`admin`), сейчас фактически один аккаунт админа.
8. Должны быть предусмотрены:
- критерии «проблема решена»;
- смена оператора;
- закрытие обращения.

## 3. Текущее состояние системы (важно для безопасного внедрения)

## 3.1 Backend

1. Стек: Go + Gin + PostgreSQL + Redis.
2. Роутинг уже разделен на:
- `/api/v1/*` для авторизованных пользователей;
- `/api/v1/admin/*` только для `role=admin`.
3. Проверка роли уже централизована (`authMiddleware`, `adminOnly`).
4. Глобальный лимит тела запроса: `MAX_REQUEST_BODY_BYTES` (по умолчанию 16 MB).
5. Миграции применяются отдельным мигратором и сортируются лексикографически.

Вывод для внедрения:

1. Новые таблицы/индексы только через новую миграцию (`038_...`), без правки старых миграций.
2. Upload-вложения упрутся в лимит тела запроса, если не спроектировать лимиты явно.

## 3.2 Frontend

1. Стек: React + TypeScript + Vite.
2. В API-клиенте есть `cachedGet` с TTL для части ручек.
3. Роль admin уже есть, маршрут `/admin` уже защищен.
4. Есть существующая политика mobile/desktop (кодинг поток ограничен на мобильных), которую нельзя ломать.

Вывод для внедрения:

1. Поддержка/чат не должна использовать «длинный» кэш чтения.
2. Нельзя вносить изменения, которые случайно вернут старые mobile/regression проблемы в layout.

## 3.3 Deploy и эксплуатация

1. Канонический деплой через `deploy/server/deploy.sh`:
- тесты;
- сборка;
- миграции отдельным бинарем;
- health/readiness checks.
2. В репозитории используется append-only подход к документации изменений.

Вывод для внедрения:

1. Релиз support-чата должен иметь отдельный rollout-чеклист.
2. Изменения документации не заменяют старые секции, а дополняют их.

## 4. Целевая модель поддержки (продуктовая логика)

## 4.1 Основные сущности

1. `Conversation` — общий чат ученика с поддержкой.
2. `Message` — сообщение внутри чата.
3. `Attachment` — файл сообщения.
4. `ConversationEvent` — системное событие (смена оператора, смена статуса, reopen и т.д.).

## 4.2 Статусы обращения и критерии «решено»

Рекомендуемая state-machine обращения:

1. `open`:
- проблема активна;
- ожидается действие администратора или ученика.
2. `resolved`:
- админ считает проблему решенной;
- добавляет комментарий решения (кратко: что сделано и почему этого достаточно).
3. `closed`:
- финальное закрытие обращения после `resolved`;
- чат остается в истории.

Правила переходов:

1. `open -> resolved`:
- только админ;
- обязательный `resolution_note`.
2. `resolved -> open`:
- автоматически при новом сообщении ученика;
- причина: решение не подтвердилось на стороне пользователя.
3. `resolved -> closed`:
- вручную админом или автоматически по SLA-таймеру (например, 72 часа без новых сообщений).
4. `closed -> open`:
- допускается только админом при необходимости реанимации кейса.

Почему именно так:

1. Состояние `resolved` отделяет «починили» от «архивировали».
2. Автоматический reopen защищает от ложного закрытия «на бумаге».
3. `closed` нужен для операционной чистоты списка обращений.

## 4.3 Смена оператора

Даже если сейчас один админ, модель закладывается мульти-операторная:

1. У разговора есть `assigned_admin_user_id` (nullable).
2. Смена оператора разрешена в `open` и `resolved`.
3. Каждая смена фиксируется в `ConversationEvent` + `admin_audit_log`.
4. При смене оператора история переписки не обнуляется и не скрывается.

Почему это важно уже сейчас:

1. Иначе при появлении второго оператора придется ломать схему БД и API.
2. История передачи ответственности критична для ревью качества поддержки.

## 5. Статусы сообщений (галочки)

Рекомендуемая модель статусов:

1. `sent`:
- сервер принял и записал сообщение.
2. `delivered`:
- сообщение доставлено на клиент получателя (через stream/pull-подтверждение).
3. `read`:
- получатель открыл диалог и подтвердил прочтение.

В UI:

1. `sent` -> одна серая галочка.
2. `delivered` -> две серые галочки.
3. `read` -> две акцентные галочки.

Почему так:

1. Поведение читается пользователем привычно (аналог мессенджера).
2. Разделение `delivered/read` важно для операционной аналитики SLA.

## 6. Архитектура realtime

Рекомендуемый first-step для текущего стека: `SSE` (`text/event-stream`).

Причины выбора:

1. Для Gin это проще и надежнее на старте, чем полный WS-брокер.
2. Быстрый ввод в эксплуатацию без смены транспортного стека frontend.
3. Для одного админа и ограниченного числа одновременных клиентов этого достаточно.

Обязательные guardrail'ы:

1. Не сжимать SSE-поток gzip (иначе возможна буферизация и псевдо-не-realtime поведение).
2. Heartbeat event каждые 15-30 секунд.
3. Reconnect на клиенте с backoff.
4. Серверные события должны быть idempotent (клиент после reconnect может перезапрашивать данные).

Когда переходить на WebSocket:

1. Если будут массовые одновременные операторы/ученики.
2. Если потребуется typing/presence/редактирование сообщений в реальном времени.

## 7. Контракт данных и БД (проектирование до кода)

## 7.1 Таблица `support_conversations`

Минимальные поля:

1. `id` UUID PK.
2. `student_user_id` UUID unique, FK -> `users(id)`.
3. `status` (`open|resolved|closed`).
4. `assigned_admin_user_id` UUID nullable, FK -> `users(id)`.
5. `resolved_at`, `resolved_by_user_id`, `resolution_note`.
6. `closed_at`, `closed_by_user_id`.
7. `last_message_at` (для сортировки списка).
8. `created_at`, `updated_at`.

Индексы:

1. `(status, last_message_at desc)`.
2. `(student_user_id) unique`.
3. `(assigned_admin_user_id, status, last_message_at desc)`.

## 7.2 Таблица `support_messages`

Минимальные поля:

1. `id` UUID PK.
2. `conversation_id` UUID FK.
3. `sender_user_id` UUID FK.
4. `body_text` TEXT nullable (разрешены сообщения только с файлами).
5. `status` (`sent|delivered|read`).
6. `delivered_at`, `read_at`.
7. `created_at`, `updated_at`.

Индексы:

1. `(conversation_id, created_at)`.
2. `(conversation_id, status)`.
3. `(sender_user_id, created_at desc)`.

## 7.3 Таблица `support_message_attachments`

Минимальные поля:

1. `id` UUID PK.
2. `message_id` UUID FK.
3. `storage_key` TEXT (путь в файловом хранилище или object storage key).
4. `original_name` TEXT.
5. `mime_type` TEXT.
6. `size_bytes` BIGINT.
7. `created_at`.

Индексы:

1. `(message_id)`.
2. `(created_at desc)`.

## 7.4 Таблица `support_conversation_events`

Для аудита статусов/передач:

1. `id` UUID PK.
2. `conversation_id` UUID FK.
3. `event_type` (`assigned`, `reassigned`, `resolved`, `reopened`, `closed`...).
4. `actor_user_id` UUID FK.
5. `payload` JSONB.
6. `created_at`.

Почему отдельная таблица событий:

1. Это позволяет доказуемо восстанавливать историю решений и смен операторов.
2. Это снижает риск «немых» изменений статуса без следа.

## 8. API-контракт (проектный)

## 8.1 Student API

1. `GET /api/v1/support/conversation`
- получить/создать общий диалог ученика.
2. `GET /api/v1/support/conversation/messages?cursor=<...>&limit=<...>`
- пагинация истории сообщений.
3. `POST /api/v1/support/conversation/messages`
- отправка сообщения (multipart/form-data);
- максимум 5 файлов.
4. `POST /api/v1/support/conversation/read`
- подтверждение прочтения входящих.
5. `GET /api/v1/support/attachments/:attachmentID`
- скачивание файла с проверкой прав.
6. `GET /api/v1/support/stream`
- realtime события (SSE).

## 8.2 Admin API

1. `GET /api/v1/admin/support/conversations`
- список чатов с фильтрами (`status`, `assignedToMe`, `q`).
2. `GET /api/v1/admin/support/conversations/:conversationID/messages`
- история сообщений по выбранному чату.
3. `POST /api/v1/admin/support/conversations/:conversationID/messages`
- ответ администратора.
4. `PATCH /api/v1/admin/support/conversations/:conversationID`
- смена статуса (`open|resolved|closed`), смена оператора.
5. `POST /api/v1/admin/support/conversations/:conversationID/read`
- подтверждение прочтения админом.
6. `GET /api/v1/support/stream`
- общий realtime stream для админа.

## 8.3 Ошибки и ограничения

Обязательные проверки на backend:

1. Пустое сообщение без файлов -> `400`.
2. Файлов больше 5 -> `400`.
3. Неверный доступ к чужому чату/вложению -> `403/404`.
4. Слишком большой файл или payload -> `413`.
5. Невалидный переход статуса (например `closed -> resolved` напрямую) -> `409`.

## 9. Безопасность вложений

Минимум, который обязателен в первой версии:

1. Санитизация имени файла (без `../`, без control-символов).
2. Запрет исполняемых расширений для inline-выдачи.
3. `Content-Disposition: attachment` для небезопасных MIME.
4. Валидация `size_bytes` и типа файла.
5. Хранилище файлов вне web-root.

Рекомендуемая production-эволюция:

1. Перейти на объектное хранилище (S3/MinIO) и presigned URLs.
2. Добавить асинхронное AV-сканирование.
3. Добавить retention-политику и удаление orphan-файлов.

## 10. Ограничения производительности и SLA

Рекомендуемые целевые метрики:

1. Открытие списка диалогов админа (P95): < 400 ms.
2. Открытие чата (50 последних сообщений, P95): < 500 ms.
3. Доставка realtime события (backend -> UI): < 2 s.
4. Отправка сообщения без файла (P95): < 300 ms.

Чтобы этого достичь:

1. Не делать N+1-запросы в списке чатов.
2. Использовать агрегацию unread в SQL/материализованных вычислениях.
3. Отдельно индексировать `last_message_at` и статусы.

## 11. Frontend внедрение без регрессий

## 11.1 Навигация

1. Для ученика добавить маршрут `/support` и видимый вход в чат.
2. Для админа не ломать текущую `/admin` аналитику:
- добавить отдельный маршрут `/admin/support` или вкладку внутри админки.

## 11.2 Состояние и кэш

1. Для чатов не использовать долгоживущий `cachedGet`.
2. После события из SSE делать целевой refetch:
- список чатов;
- активный диалог;
- статусы сообщений.

## 11.3 UI-правила

1. Время сообщений показывать в локальном часовом поясе пользователя.
2. Вложения показывать отдельным блоком по сообщению.
3. Статусы галочек только для исходящих сообщений текущего пользователя.
4. Для long uploads обязательно progress/disabled состояние кнопки отправки.

## 11.4 Accessibility

1. Поля/кнопки с aria-label.
2. Контраст и focus states не ниже текущих стандартов проекта.
3. Клавиатурная отправка:
- Enter отправляет;
- Shift+Enter новая строка.

## 12. Пошаговый план внедрения (для инженера, который будет делать)

## Этап 0. Preflight

1. Зафиксировать продуктовые статусы (`open/resolved/closed`) и SLA авто-закрытия.
2. Зафиксировать лимиты:
- максимум 5 файлов;
- размер файла;
- общий размер запроса.
3. Добавить feature flag `SUPPORT_CHAT_ENABLED` (backend + frontend).

## Этап 1. Backend schema + read API

1. Добавить миграцию `038_support_chat_core.sql`.
2. Добавить read-only ручки списка/истории без отправки файлов.
3. Добавить unit/integration тесты SQL-агрегации unread и сортировки.

## Этап 2. Message send + attachments

1. Реализовать отправку сообщения с лимитом 5 файлов.
2. Реализовать безопасную выдачу вложений.
3. Добавить тесты:
- ограничения;
- авторизация доступа к вложению;
- path traversal negative tests.

## Этап 3. Realtime + statuses

1. Добавить SSE поток и события.
2. Реализовать переходы `sent -> delivered -> read`.
3. Проверить деградацию при reconnect и дубликатах событий.

## Этап 4. Admin operations

1. Добавить `resolved/closed/reopen`.
2. Добавить назначение/смену оператора.
3. Добавить audit trail в `support_conversation_events` + `admin_audit_log`.

## Этап 5. Frontend UX

1. Страница ученика `/support`.
2. Админский список диалогов + окно переписки.
3. Реализовать статусы галочек и unread.
4. Добавить mobile-адаптацию без нарушения существующих policy.

## Этап 6. Release

1. Прогнать backend tests + frontend tests/build.
2. Прогнать smoke на staging:
- отправка текста;
- отправка 5 файлов;
- realtime;
- resolved/closed/reopen;
- смена оператора.
3. Выкатить с feature flag.
4. После наблюдения метрик включить всем.

## 13. Обязательный anti-regression checklist перед merge

1. `go test ./...` зеленый.
2. `npm run test` и `npm run build` зеленые.
3. Не изменены существующие auth/billing/learning endpoint-контракты.
4. Не деградирован `GET /readyz`.
5. Не появилось неконтролируемых длинных транзакций в БД.
6. Вложения не отдаются неавторизованному пользователю.
7. Список чатов и история не используют N+1.
8. SSE не блокируется gzip/прокси-буфером.
9. Статусы галочек консистентны после reconnect.
10. Для `resolved` обязателен `resolution_note`.

## 14. Критичные ошибки, которые нельзя допустить

1. Сохранять вложения в публичной директории frontend.
2. Отдавать вложения без проверки участника conversation.
3. Хранить чат-состояние только во frontend кэше без серверной модели.
4. Закрывать диалог без истории событий (невозможно расследовать инциденты).
5. Вводить state-machine без `reopen` при новом сообщении ученика.
6. Обновлять существующие миграции вместо новой.
7. Ломать существующие `/admin` метрики или ролевой middleware.

## 15. Definition of Done (DoD) для внедрения

Считать задачу внедренной только если одновременно выполнено:

1. Ученик может открыть единый чат поддержки и отправлять:
- текст;
- до 5 вложений.
2. Админ видит Telegram-подобный список чатов с:
- последним сообщением;
- временем;
- unread.
3. Сообщения имеют рабочие статусы `sent/delivered/read` с корректными галочками в UI.
4. Есть рабочие переходы `open/resolved/closed` и `reopen`.
5. Есть назначение/смена оператора с аудитом.
6. Realtime события стабильно доставляются.
7. Пройдены авто-тесты + smoke + deploy-check.
8. Документация обновлена append-only (README + changelog + API/ops заметки).

## 16. Почему такой blueprint не является «костылем»

1. Проектирование начинается с доменной модели и state-machine, а не с «быстрого UI».
2. Сразу закладывается операционный контур:
- аудит;
- SLA;
- безопасность файлов;
- rollout/rollback.
3. Архитектура совместима с текущим стеком, но не блокирует эволюцию в сторону multi-operator и object storage.
4. Фиксируются четкие gate-критерии, поэтому внедрение можно ревьюить по объективным пунктам, а не по субъективному «вроде работает».
