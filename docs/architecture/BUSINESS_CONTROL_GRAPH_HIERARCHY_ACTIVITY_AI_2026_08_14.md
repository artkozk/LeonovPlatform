# Архитектура графа, иерархии, активности и ИИ-подсказок

Дата: 14 августа 2026 года.

## 1. Миграции данных

`004_record_priority.sql` добавляет `records.priority` с закрытым перечислением `low | normal | high | critical` и индексом для рабочей сортировки.

`005_collaboration_hierarchy_activity.sql` добавляет:

- `records.workstream` с перечислением `business | platform | operations`;
- `records.edit_policy` с перечислением `shared | owner_only`;
- `records.parent_id` как внешний ключ на `records(id)` с `ON DELETE RESTRICT`;
- `records.is_root`;
- `records.actual_minutes`;
- таблицу `user_activity_daily` с уникальной парой `(user_id, activity_date)`;
- индексы рабочей очереди и родительской иерархии.

Все новые поля имеют безопасные значения по умолчанию, поэтому существующие записи после миграции остаются общими бизнес-карточками с обычным приоритетом, без родителя и без фактического времени.

## 2. Инварианты прав

`requireRecordEdit` применяется ко всем изменяющим операциям карточки: основной PATCH, архив, разделы, связи, оценки, уведомления, вопросы, совместные решения и производные результаты.

Правила:

1. `owner_only` изменяет только `owner_id` этой карточки.
2. В `shared` оба участника меняют рабочие данные.
3. `owner_id` и `edit_policy` меняет только текущий владелец даже в `shared`.
4. Личный ответ на вопрос проверяет автора ответа и остаётся доступным каждому участнику независимо от политики контейнера.
5. Для общей задачи доказательство и завершение доступны обоим участникам; для личной — только владельцу.

Проверки выполняются в backend. Frontend повторяет их для объяснения состояния и блокирует недоступные элементы.

## 3. Иерархия

Иерархия хранится отдельно от `record_links`:

- `parent_id` означает единственного структурного родителя;
- `record_links` остаётся many-to-many причинным и смысловым графом.

Разделение нужно, потому что связь `поддерживает` или `создано из` не всегда означает подчинённость. Визуальная карта объединяет оба вида рёбер, но backend сохраняет разные контракты.

При смене родителя `parentCreatesCycle` поднимается по цепочке максимум на 256 уровней. Встреча исходной карточки означает цикл и отклоняет запрос. Установка `is_root=true` очищает `parent_id`. Установка непустого `parent_id` очищает `is_root`.

## 4. API

Новые endpoint:

- `GET /api/graph` — агрегированный граф записей, вопросов, ответов, совместных итогов, явных ссылок, критериев, производных связей и иерархии;
- `GET /api/search?q=...` — общий поиск по карточкам и содержимому обсуждений;
- `POST /api/presence` — ограниченный heartbeat активного времени и числа взаимодействий;
- `GET /api/users/{id}/profile` — 30-дневная активность, действия, завершённые работы, план/факт и последние события;
- `POST /api/ai/suggest-record` — проверенная подсказка `priority`, `workstream`, `parentId`, `reason`, `source`.

`GET /api/graph` и детальная карточка отдают `Server-Timing`. Основные данные карточки не ждут `/relations`; связи загружаются отдельным endpoint только по запросу вкладки.

## 5. Граф

Cytoscape.js `3.34.1` хранится в `web/vendor` вместе с лицензией и встраивается в бинарник. Это устраняет runtime-зависимость от CDN и соответствует закрытой CSP.

Идентификаторы узлов имеют namespace:

- `record:{recordId}`;
- `question:{questionId}`;
- `answer:{answerId}`;
- `decision:{decisionId}`.

Идентификаторы рёбер также имеют префиксы по источнику данных. Это предотвращает коллизии между таблицами и позволяет frontend различать семантику.

Граф ограничивает карточки до 2000 актуальных записей. Это достаточный предел закрытого контура. Перед многопользовательским запуском потребуется серверная подгрузка локального окружения и кластеризация больших графов.

## 6. Активность

Frontend отправляет heartbeat раз в 30 секунд. В активное время включается только интервал, если последнее пользовательское взаимодействие было не более 90 секунд назад. Сервер ограничивает один heartbeat 120 секундами и 500 взаимодействиями, чтобы ошибочный клиент не мог бесконтрольно увеличивать метрики.

Агрегация выполняется UPSERT по UTC-дню. Аудит действий остаётся отдельной таблицей `activity`; heartbeat не создаёт событие на каждое касание и не засоряет историю проекта.

## 7. Groq

Конфигурация:

- `GROQ_API_KEY` — необязательный секрет;
- `GROQ_MODEL` — модель, по умолчанию `openai/gpt-oss-20b`.

Backend использует OpenAI-совместимый `POST /openai/v1/chat/completions`, таймаут 12 секунд и `response_format: json_object`. В промпт передаются тип, заголовок, описание и максимум 40 возможных корневых карточек. Ответ валидируется локально. Неизвестный `parentId` отбрасывается.

Если ключ отсутствует, сеть недоступна, Groq возвращает ошибку или JSON не проходит валидацию, используется эвристический ответ. Создание карточки не становится зависимым от ИИ.

## 8. Проверка и rollback

Обязательные проверки перед релизом:

```powershell
cd C:\prog\Comercial\LeonovCarePlatform\business-control
gofmt -w internal\app\*.go
node --check web\app.js
go test ./...
go vet ./...
```

Перед production миграцией копируется SQLite-файл и его WAL/SHM-состояние безопасно сворачивается остановкой сервиса или SQLite backup. Rollback бинарника без rollback базы допустим: старый код игнорирует новые nullable/default-поля. Полный rollback использует резервную копию до миграции.
