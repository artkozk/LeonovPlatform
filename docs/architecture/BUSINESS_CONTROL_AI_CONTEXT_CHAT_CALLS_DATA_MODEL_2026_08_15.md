# Архитектура жизненных циклов, AI-контекста, чата и звонков BizFlow

Дата актуализации: 15 августа 2026 года.

## Архитектурная цель

Релиз устраняет смешение трёх разных понятий: объект знания, исполняемая работа и факт принятого решения. Все они остаются карточками и могут связываться, но имеют разные инварианты жизненного цикла.

## Инварианты записей

### Решение

- `type=decision`.
- При создании нормализуется в `status=completed` и `progress=100`.
- `completed_at` заполняется сервером.
- `due_at`, `estimate_minutes` и `actual_minutes` очищаются.
- API не принимает управляемый прогресс и планирование решения.
- Решение исключается из вычисляемой рабочей очереди.

Миграция `008_decision_and_research_semantics.sql` приводит существующие решения к этой модели.

### Исследование

Прогресс возвращается в API как вычисляемое значение. Он зависит от базового контекста, вариантов, сравнительных полей, заполненности и результата. Клиент не является источником истины для прогресса.

`POST /api/records/{id}/complete-research` атомарно проверяет результат, предметный материал и причину. Только этот маршрут переводит исследование в завершённое состояние. Обычный `PATCH` не может подменить предметную операцию.

### Задача на проверке

`status=review` остаётся активным даже при `progress=100`, потому что действие постановщика ещё не выполнено. Доска не выполняет переход напрямую: клиент открывает предметный сценарий результата и доказательства, а сервер проверяет его повторно.

## Полное AI-досье

`buildAIRecordContext` собирает структурированный объект из доступных таблиц:

- основная запись и смысловые разделы;
- `research_option_fields`, `research_options`, `research_option_values`;
- внешние связи и связанные записи;
- критерии и оценки;
- вопросы, ответы и совместные решения;
- комментарии, чек-лист и доказательства;
- метаданные вложений;
- происхождение производных объектов;
- журнал изменений.

Параллельно формируется `AIContextCoverage`: количество секций, вариантов, полей, связей, критериев, вопросов, ответов, решений, комментариев, шагов, доказательств, файлов и событий. Если серверный лимит требует усечения, ответ содержит признак truncation. Это исключает ситуацию, когда модель молча анализирует один заголовок вместо заполненного исследования.

Провайдеры вызываются одним HTTP-клиентом с обязательным proxy transport при заданном `AI_PROXY_URL`. Порядок: Gemini, Groq, локальный fallback. Ответ провайдера валидируется до отправки клиенту. Сохранение или создание сущности выполняется только отдельным пользовательским запросом.

## Модель чата

Миграция `009_team_chat.sql` добавляет:

- `chat_threads`: общий или предметный диалог;
- `chat_members`: участники и отметка последнего чтения;
- `chat_attachments`: файл, MIME, размер, SHA-256 и физическое имя;
- `chat_messages`: текст, ответ, связанная карточка, вложение, тип, время изменения и мягкой архивации;
- `chat_reactions`: реакция пользователя на сообщение;
- `chat_favorites`: персональное избранное;
- `chat_calls`: сигналинг, состояния и временные метки звонка;
- `chat_call_candidates`: ICE-кандидаты для P2P-соединения.

Миграция `010_chat_message_history.sql` добавляет `chat_message_revisions`. Для edit сохраняются старое и новое значения. Для archive сохраняется старое значение и обязательная причина. Удаление строки сообщения и файла не выполняется.

## Права чата

- Все маршруты требуют активную сессию.
- Сообщения и звонки доступны только участнику потока.
- Редактировать и архивировать можно только собственное текстовое сообщение.
- Связанная карточка проходит обычную проверку доступа.
- Файл скачивается через авторизованный маршрут, а не как публичная статика.
- Точный список прочитавших строится из `chat_members.last_read_at` и времени сообщения.
- Создание второго звонка запрещено при `ringing` или `active` в том же потоке.
- Ответить может только другой участник.

Основные маршруты:

```text
GET    /api/chat/threads
POST   /api/chat/threads
GET    /api/chat/threads/{threadId}/messages
POST   /api/chat/threads/{threadId}/messages
POST   /api/chat/threads/{threadId}/read
PATCH  /api/chat/messages/{messageId}
DELETE /api/chat/messages/{messageId}
POST   /api/chat/messages/{messageId}/reaction
POST   /api/chat/messages/{messageId}/favorite
POST   /api/chat/threads/{threadId}/attachments
GET    /api/chat/attachments/{attachmentId}
POST   /api/chat/threads/{threadId}/ai-digest
GET    /api/chat/ice-config
POST   /api/chat/threads/{threadId}/calls
GET    /api/chat/threads/{threadId}/calls/active
POST   /api/chat/calls/{callId}/answer
POST   /api/chat/calls/{callId}/candidates
GET    /api/chat/calls/{callId}/candidates
POST   /api/chat/calls/{callId}/end
```

## ICE и TURN

Настройки читаются только из server environment:

```text
BUSINESS_CHAT_STUN_URL
BUSINESS_CHAT_TURN_URL
BUSINESS_CHAT_TURN_USERNAME
BUSINESS_CHAT_TURN_CREDENTIAL
```

`GET /api/chat/ice-config` доступен только после авторизации. Frontend сначала получает этот набор и только затем создаёт `RTCPeerConnection`. Встроенный JavaScript не содержит production-учётные данные.

Текущая модель TURN использует статическую пару логина и длинного случайного пароля. Это приемлемо для закрытого контура двух пользователей, но при независимых организациях нужно перейти на краткоживущие TURN credentials, отдельные tenant realm и лимиты трафика.

WebRTC шифрует медиапоток DTLS-SRTP. Это не означает end-to-end модель уровня защищённого мессенджера: сигналинг, метаданные и TURN остаются частью доверенного серверного контура.

## Клиентская доска

Сервер остаётся источником состояния. Pointer drag только выбирает целевую колонку, после чего обычный API перехода требует причину и проверяет допустимость. Нативный drag-and-drop и меню перемещения остаются альтернативными способами вызова той же операции.

Для активной очереди используется единая функция `isWorkRecord`. Решения и неактивные состояния исключаются; 100% исключается, кроме review. Это правило применяется к главной, списку, доске, загрузке команды и выбору связей, чтобы разные экраны не противоречили друг другу.

## Аудит и тесты

`lifecycle_chat_test.go` защищает следующие сценарии:

- нормализация решения;
- вычисляемый прогресс и предметное завершение исследования;
- включение сравнительных данных в AI-досье;
- выдача STUN/TURN только через авторизованный endpoint;
- непрочитанные сообщения, ответ, реакция, избранное и точное чтение;
- права изменения сообщения и сохранение двух ревизий;
- защита звонка от дублирования и самопринятия.

Существующие workflow-тесты продолжают проверять доказательства задач, проверку постановщиком, вложения, права, сохранённые представления и уведомления.
