# Deployment Runbook

## 1. Цель

Развернуть Leonov Care как отдельную площадку в новой директории на сервере, с отдельными портами и независимыми процессами.

## 2. Целевые порты

- API: `8510`
- Frontend: `8511`
- PostgreSQL (локальный сервис): `5432`
- Redis (локальный сервис): `6379`

## 3. Подготовка сервера

1. Установить системные зависимости:
- `git`
- `curl`
- `build-essential`
- `golang`
- `redis-server`

2. Создать директорию:
- `/opt/leonovcare-platform`

3. Клонировать репозиторий в отдельный путь.

## 4. Конфигурация backend

1. Скопировать `backend/.env.example` -> `backend/.env`.
2. Заполнить секреты JWT.
3. Указать `HTTP_PORT=8510`.
4. Настроить `DATABASE_URL` и `REDIS_URL`.
5. Для Cardlink после получения реквизитов заполнить:
- `CARDLINK_MERCHANT_ID`
- `CARDLINK_SECRET`
- `CARDLINK_WEBHOOK_TOKEN`
6. Для AI-подсказок (OpenAI) заполнить:
- `OPENAI_API_KEY`
- `OPENAI_BASE_URL` (если нужен не-default endpoint)
- `OPENAI_MODEL`
7. Для Google OAuth заполнить:
- `GOOGLE_CLIENT_ID`

## 5. Сборка

1. Backend:

```bash
cd backend
go mod tidy
go build -o bin/leonovcare-api ./cmd/server
go build -o bin/leonovcare-worker ./cmd/worker
```

2. Frontend:

```bash
cd frontend
npm install
npm run build
```

## 6. Запуск через PM2

1. Импорт `deploy/server/ecosystem.config.cjs`.
2. `pm2 start ecosystem.config.cjs`
3. `pm2 save`

## 7. Проверки качества после деплоя

1. `curl http://127.0.0.1:8510/healthz`
2. Открыть `http://<server-ip>:8511`
3. Регистрация пользователя
4. Прохождение демо-задачи
5. Проверка лидборда
6. Проверка checkout (режим `pending_config` до merchant id)

## 8. Почему именно такой процесс

- PM2 уже используется на сервере, это снижает риск операционных ошибок.
- Отдельные порты и директория дают полную изоляцию новой площадки от существующих сервисов.
- Runbook фиксирует повторяемый deployment-процесс для дальнейших релизов.

## 9. Дополнение от 2026-04-23 (production fix)

1. На этапе frontend build обязательно задаётся `VITE_API_URL`:
- пример: `http://85.198.82.221:8510/api/v1`

2. Почему это критично:
- без явного `VITE_API_URL` фронтенд может использовать дефолтный `localhost:8080`, и API вызовы у учеников будут падать.

3. Для внешнего доступа к площадке нужно открыть порты через UFW:
- `ufw allow 8510/tcp`
- `ufw allow 8511/tcp`

4. Почему это сделано именно так:
- площадка развёрнута как отдельный сервис, поэтому открываются только её целевые порты, без изменения правил для других приложений.

## 10. Дополнение от 2026-04-23 (AI hint enablement)

1. Production-подсказки используют `POST /api/v1/ai/task-hint`.
2. Если `OPENAI_API_KEY` не задан, endpoint возвращает `pending_openai_config`.

## 13. Дополнение от 2026-04-28 (PM2 env source and zero-downtime rollback path)

1. Источник боевых секретов и инфраструктурных переменных для backend/worker:
- `backend/.env` в каталоге текущего релиза.

2. PM2-конфиг (`deploy/server/ecosystem.config.cjs`) должен читать `backend/.env` и только после этого применять `process.env` как override.

3. Пошаговый безопасный rollout:
- собрать релиз-архив из git;
- распаковать в отдельный `current_new_<timestamp>`;
- перенести `backend/.env` и `frontend/.env` из старого `current`;
- переключить директорию `current` атомарно (`mv current -> backup`, `mv current_new -> current`);
- выполнить `deploy/server/deploy.sh`;
- проверить `pm2 list`, `curl http://127.0.0.1:8510/healthz`, `curl -I http://127.0.0.1:8511`.

4. Пошаговый rollback:
- остановить процессы LeonovCare в PM2;
- вернуть директорию `current` на предыдущий `current_backup_<timestamp>`;
- запустить `deploy/server/deploy.sh` из rollback-версии;
- повторить health-check.

Почему это сделано именно так:

1. Исключается падение API/worker из-за дефолтных fallback-значений (`postgres:postgres`) при отсутствии явных env в shell PM2.
2. Атомарный переключатель `current` оставляет быстрый путь отката без пересборки и без восстановления из внешнего бэкапа.
3. Разделение `build -> switch -> verify` делает деплой воспроизводимым для релизов перед запуском на когорту ~200 студентов.

## 14. Дополнение от 2026-04-29 (production payments and subscription access)

1. Обязательные переменные для рабочего Cardlink checkout:
- `CARDLINK_BASE_URL` (пример: `https://cardlink.link`)
- `CARDLINK_SHOP_ID`
- `CARDLINK_API_TOKEN`
- `CARDLINK_CURRENCY_IN` (`RUB` по умолчанию)
- `CARDLINK_BILL_TTL_SECONDS` (по умолчанию `1800`)

2. Дополнительные переменные для UX-редиректов:
- `CARDLINK_SUCCESS_URL`
- `CARDLINK_FAIL_URL`
- `CARDLINK_RETURN_URL`

3. Переменные для webhook-валидации:
- Form postback Cardlink: подпись проверяется как `strtoupper(md5(OutSum:InvId:apiToken))` через `CARDLINK_API_TOKEN`.
- Legacy JSON webhook (внутренний): остаются `CARDLINK_WEBHOOK_TOKEN` и `X-Cardlink-Signature` (HMAC).

4. Обязательный post-deploy smoke-test платежей:
1. Авторизоваться пользователем с `free` планом.
2. Создать checkout на `pro`/`premium`.
3. Проверить, что API вернул `paymentId` и `checkoutUrl`.
4. Проверить `GET /api/v1/subscription/payments/:paymentId?sync=true`.
5. Провести тестовый платеж в Cardlink.
6. Проверить переход статуса платежа в `paid`.
7. Проверить, что `GET /api/v1/subscription` отражает новый план и `endsAt`.
8. Проверить ограничение AI-hints:
- `premium` должен проходить;
- `free/pro` должны получать `upgrade_required`.

5. Сценарии, которые обязательно прогоняются перед релизом:
1. Повторный клик по оплате до завершения первого платежа:
- ожидается reuse существующего pending checkout (без создания дубля).
2. Недоплата (`UNDERPAID`):
- подписка не должна активироваться.
3. Провал (`FAIL`):
- активная подписка не должна ложнопозитивно обновиться.
4. Refund/chargeback:
- активная подписка, привязанная к этому платежу, должна быть отозвана.
5. Отмена подписки пользователем:
- автопродление выключается;
- оплаченный доступ действует до `endsAt`.

Почему это сделано именно так:

1. Контур оплаты должен быть наблюдаемым и проверяемым по API, чтобы поддержка могла подтвердить состояние заказа без ручных SQL-проверок.
2. Комбинация webhook + `sync` endpoint закрывает риск рассинхронизации статусов при сетевых сбоях.
3. Проверка edge-case сценариев (дубли, недоплата, refund) критична до запуска на массовую когорту.

## 19. Дополнение от 2026-04-29 (разбор инцидента: submission зависает в `В очереди`)

1. Симптом на UI:
- после `Отправить на проверку` статус долго остается `В очереди` без финального verdict.

2. Как быстро проверить корень на production:
1. Проверить worker-логи:
```bash
pm2 logs leonovcare-worker --nostream --lines 200
```
2. Ищем две сигнатуры ошибок:
- `ERROR: column reference "id" is ambiguous (SQLSTATE 42702)`;
- `ERROR: could not determine data type of parameter $2 (SQLSTATE 42P18)`.

3. Техническая причина:
- в `processSubmissionByID` использовался `WHERE id = $1` в запросе с `JOIN submissions s` и `tasks t`, что приводило к SQL ambiguity;
- в `handleSubmissionProcessingError` параметр `$2` для `run_log` не имел явного типа, и PostgreSQL не мог вывести тип в `CONCAT(...)`.

4. Почему submission остается `queued`:
- job извлекается воркером из Redis (BLPOP);
- основная обработка падает на SQL ambiguity;
- retry-ветка тоже падает до успешного `UPDATE`/`RPUSH`;
- в итоге submission в БД не завершен, а job уже потерян из очереди.

5. Исправление в коде:
- `WHERE s.id = $1` в `backend/internal/app/worker.go`;
- `$2::text` в обоих `run_log` update выражениях retry-ветки.

6. Post-fix проверка после деплоя:
1. Создать новую отправку на любой учебной задаче.
2. Проверить, что статус меняется `queued -> processing -> accepted/wrong_answer`.
3. Убедиться, что в `pm2 logs leonovcare-worker` больше нет SQLSTATE `42702` и `42P18`.

Почему это зафиксировано в runbook:

1. Инцидент воспроизводится только на реальной очереди и заметен пользователю как «вечное ожидание», поэтому нужен отдельный операционный сценарий диагностики.
2. Сигнатуры двух SQL-ошибок позволяют быстро отличить этот дефект от проблем Redis, judge runtime или frontend polling.

## 20. Дополнение от 2026-04-29 (AI hint: fallback при `403 Country, region, or territory not supported`)

1. Симптом:
- на `POST /api/v1/ai/task-hint` backend возвращает `502 ai hint failed`.

2. Диагностика:
1. Проверить API-логи:
```bash
pm2 logs leonovcare-api --nostream --lines 200
```
2. Проверить таблицу `ai_hint_requests`:
```sql
SELECT created_at, status, model, error_text
FROM ai_hint_requests
ORDER BY created_at DESC
LIMIT 20;
```
3. Сигнатура инцидента:
- `openai status 403: Country, region, or territory not supported`.

3. Техническая причина:
- внешний OpenAI endpoint недоступен для текущего server-region/route;
- приложение получает валидный ответ-ошибку провайдера, но раньше транслировало это как `502` пользователю.

4. Текущее поведение после фикса:
- при таком `403` backend переключается на локальный fallback-hint;
- API возвращает `200` с `model=local-fallback` и безопасной учебной подсказкой.

5. Что проверить после деплоя:
1. Нажать `AI-подсказка` в уроке/задаче.
2. Убедиться, что UI показывает текст подсказки, а не `ai hint failed`.
3. В `ai_hint_requests` должна появиться запись со статусом `fallback_region_restricted`.

Почему это сделано именно так:

1. Этот класс ошибки зависит от внешнего провайдера и маршрутизации, поэтому runtime должен иметь устойчивый резервный режим.
