# PROMOCODE_UNLIMITED_20_CODES_2026_06_17

## Кратко

17 июня 2026 обнаружено, что рабочие `20` промокодов периодически перестают проходить у разных пользователей, потому что backend продолжал применять строго «одноразовую» модель для всех записей `promo_codes`. Из-за этого второй/третий заход по одному коду получал конфликт или 409 даже для тех кейсов, где по бизнес-требованию коды должны были быть многоразовыми для запуска.

## Почему это ломало сценарий

1. В `POST /api/v1/subscription/promocode/apply` блокировка была только по общим полям:
   - `pc.redeemed_by_user_id`,
   - `pc.redeemed_at`,
   - `provider_payment_id = 'PROMO-'||promoID`.
2. Для кода, который уже помечен как использованный хотя бы раз, endpoint сразу возвращал:
   - `409 promo code already redeemed` или `409 promo code already redeemed by this account`;
3. Для многократного режима это невалидно, т.к. тот же код должен активировать подписку у каждого пользователя.
4. Даже при попытке снять эту блокировку на уровне платежа `provider_payment_id` оставался фиксированным на код, что при уникальном индексе `payments(provider, provider_payment_id)` приводило к конфликтам.

## Что исправлено

### 1) Добавлен флаг многоразовости

В `backend/internal/app/handlers_billing.go` (`ApplyPromoCode`) добавлены проверки на `pc.is_reusable`:

1. Если `is_reusable = false` — поведение осталось прежним:
   - блоки `already redeemed`,
   - синхронизация `redeemed_by_user_id`/`redeemed_at`,
   - финальное обновление строки в `promo_codes`.
2. Если `is_reusable = true` — лимит по одному использованию отключается:
   - проверки `redeemed_by_user_id`/`redeemed_at` пропускаются,
   - `provider_payment_id` формируется уникальным (`PROMO-<promoID>-<uuid>`),
   - финальное обновление `redeemed_*` для кода не выполняется.
3. `suggestPromoCodeWithSingleExtraCharTx` теперь не фильтрует `redeemed_*` для `is_reusable`:
   - для многократных кодов подсказка по одной лишней букве продолжает работать.

### 2) Добавлена миграция и переведены целевые 20 кодов

В `backend/migrations/045_promocode_unlimited_20_codes_2026_06_17.sql`:

1. Добавлен столбец `promo_codes.is_reusable BOOLEAN NOT NULL DEFAULT FALSE`.
2. Явно помечены в `TRUE` коды из двух кампанийных пулов (в сумме 20):
   - 5 `START` и 5 `PREM` из `044`/`042`-сетов.
3. Для этих кодов очищены `redeemed_by_user_id` и `redeemed_at`, чтобы «перезапуск» не зависел от старых отметок.

## Почему так

1. Решение точечно меняет только те коды, которые должны быть многоразовыми, и не ломает контракт промокодов с гарантией одноразовости.
2. Уникальность платежа сохранена и не конфликтует с `idx_payments_provider_payment_id_unique`, потому что для безлимитного использования `provider_payment_id` теперь уникален для каждой активации.
3. Отдельная миграция с явным списком кодов исключает «тихий» массовый рефактор поведения для потенциальных будущих промокодов.

## Что проверить после развёртывания

1. Повторный запрос `POST /api/v1/subscription/promocode/apply` тем же кодом разными аккаунтами:
   - должен возвращать `200`, а не `409`, для помеченных в `is_reusable=true`.
2. Проверка запроса уже использованного одноразового кода:
   - должен оставаться `409` (чтобы не затронуть legacy-режим).
3. В БД:
   - у целевых 20 кодов `is_reusable=true`,
   - у них не должно быть постоянной блокировки из `redeemed_by_user_id`/`redeemed_at`.
4. Логи API:
   - отсутствуют 500/42P10/неожиданные `23505` при корректном повторном применении безлимитных кодов.
