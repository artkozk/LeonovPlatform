# AUTH_PASSWORD_MINLEN_REGRESSION_FIX_2026_06_03

## Кратко

Фиксируется отказ входа в админку с ошибкой `пароль минимум 8 символов` при использовании существующего админ-пароля длиной 6 символов.

## Что именно было сломано

1. В форме авторизации в `frontend/src/pages/AuthPage.tsx` у поля пароля стояло жёсткое `minLength={8}`.
2. Компонент общий для режимов:
   - `mode === "login"` (вход),
   - `mode === "register"` (регистрация).
3. Из‑за этого браузерная валидация блокировала отправку формы входа для 6-символьного пароля, хотя API разрешает такой `login` (минимум проверяется только на регистрации).

## Почему не даунгрейд

Это не даунгрейд по сути. Это регресс по валидации UI после первого импорта/запуска страницы, где проверка длины не была разнесена по режимам. Бизнес-правило бэкенда:
- регистрация: минимум 8 (`registerRequest.Password`),
- вход: без минимальной длины в `loginRequest`.

То есть по контракту API вход с 6 символами допустим, а UI должен был это поддерживать.

## Что исправлено

1. В `AuthPage.tsx` для поля пароля изменён минимум длины:
   - `register`: `minLength={8}`,
   - `login`: без `minLength`.
2. Обновлён фронтовый бандл (`frontend/dist/...`) после сборки, чтобы продакшен-экземпляр грузил правильную версию, а не кэшированный/старый артефакт.

## Почему сделано именно так

1. Разделение по режимам соответствует реальным правилам:
   - регистрация требует более строгого порога,
   - вход должен доверять серверной проверке.
2. Разрешение на уровне UI убирает ложноположительный отказ, не меняя серверную модель безопасности.
3. Пересборка dist обязательна для production, чтобы убрать расхождение между кодом в репозитории и тем, что реально отдаёт `/` на сервере.

## Проверка после фикса

1. Открыть `/auth` → вкладка `Вход`.
2. Ввести email админа и пароль из 6 символов.
3. Подтвердить, что форма отправляется, и после ответа API происходит редирект в защищённую зону (`/admin` / `/dashboard` в зависимости от роли).
4. Оставшиеся пути:
   - регистрация по-прежнему требует `>= 8` символов;
   - проверка на backend `loginRequest` подтверждается отсутствием ошибки `min` от API на входе.

## Постфактум по инциденту `bad request` после публикации

### Что произошло

1. После фикса `1a7f42c` (03.06.2026, 22:12) в репозитории уже была правильная валидация:
   - `login` (`mode === "login"`) — `minLength` не задан;
   - `register` — `minLength=8`.
2. На боевом сервере до повторного деплоя продолжал лежать старый `frontend/dist` из предыдущего билда (`index-DJHEs998.js`), где в `password`-поле было `minLength:8` для всех режимов.
3. Из‑за этого часть клиентов продолжала видеть сообщение про 8 символов и работала на неверном JS-артефакте, хотя исходный код в репозитории был уже исправлен.

### Как проверялось

1. Сравнение бандлов:
   - старая версия содержала `minLength:8` в password-инпуте;
   - новая версия содержит `minLength:p==="register"?8:void 0`.
2. Контракт `/api/v1/auth/login` подтверждён:
   - корректный запрос с невалидными учётными данными возвращает `401 {"error":"invalid credentials"}`;
   - серверная валидация входа не требует минимум 8 символов.
3. `400 bad request` по ручным `curl`-запросам почти всегда означает некорректно сформированное тело запроса, а не бизнес-валидацию пароля.

### Что сделано и почему

1. Выполнена пересборка фронта и деплой нового `frontend/dist` в `/opt/leonovcare-platform/current/frontend/dist`.
2. Перезапущен сервис `leonovcare-frontend` через `pm2 restart`.
3. Это устраняет регрессию в проде без отката backend и без изменения security-политики.
