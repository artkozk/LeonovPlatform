# Production Deployment Report — 2026-04-23

## 1. Контекст

Развернута отдельная площадка Leonov Care в отдельной директории сервера:

- `server`: `85.198.82.221`
- `path`: `/opt/leonovcare-platform/current`
- `api`: `:8510`
- `frontend`: `:8511`

Решение намеренно вынесено в отдельный путь и порты, чтобы не пересечься с существующими сервисами на сервере.

## 2. Что установлено на сервере

1. `golang-go` (1.22.2)
2. `default-jdk` (OpenJDK 21)
3. `redis-server`

Почему именно так:

- Go нужен для сборки backend.
- JDK нужен для проверки Java-решений.
- Redis нужен для асинхронной очереди отправок задач.

## 3. Что настроено

1. PostgreSQL:
- пользователь: `leonovcare`
- БД: `leonovcare_platform`

2. PM2 процессы:
- `leonovcare-api`
- `leonovcare-worker`
- `leonovcare-frontend`

3. ENV backend:
- `DATABASE_URL=postgres://leonovcare:***@127.0.0.1:5432/leonovcare_platform?sslmode=disable`
- `REDIS_URL=redis://127.0.0.1:6379/0`
- JWT секреты
- Cardlink webhook token

## 4. Проверки после деплоя

1. `curl http://127.0.0.1:8510/healthz` → `200`.
2. Frontend health на `:8511` → `200`.
3. Smoke script `tests/smoke.sh` → `Smoke OK`.
4. E2E-путь (register -> course -> task submit) отрабатывает, в БД есть accepted submissions.

## 9. Дополнительный production-fix (v1.1)

1. Симптом:
- внешний запрос к `http://85.198.82.221:8511` давал timeout, при том что локально на сервере `:8511` отвечал.

2. Причины:
- UFW не имел allow-правил для `8510/8511`.
- в production build фронтенда не фиксировался `VITE_API_URL`, из-за чего был риск ухода запросов на `localhost:8080`.

3. Исправления:
- добавлены правила:
  - `ufw allow 8510/tcp`
  - `ufw allow 8511/tcp`
- в `deploy/server/deploy.sh` добавлен:
  - `export VITE_API_URL="${VITE_API_URL:-http://85.198.82.221:8510/api/v1}"`

4. Почему сделано именно так:
- это минимальное и достаточное изменение, чтобы площадка работала извне сразу после стандартного deployment сценария.
- изменён именно deploy-процесс, а не ручной runtime, чтобы решение было повторяемым на релизах.

## 29. Light-only UI update (2026-05-02)

1. Исторический пункт v1.19 про `dark-mode через токены` оставлен выше как описание прошлой версии.
2. Текущее production-состояние:
- пользовательский `/settings` удалён из frontend router;
- пункт `Настройки` удалён из profile-menu;
- `/profile` больше не показывает карточку перехода к настройкам;
- frontend всегда использует светлую тему;
- backend возвращает и сохраняет `theme: "light"`.
3. Добавлена миграция `024_light_theme_only.sql`, чтобы старые production-строки `user_settings.theme='dark'` не могли вернуть тёмную палитру после деплоя.

Почему это важно:

1. Dark-mode визуально ухудшал продукт и не должен участвовать в production-проверке.
2. Settings не является нужным экраном для первой когорты учеников.
3. Compatibility на backend сохранён, чтобы релиз не требовал рискованного удаления колонки и не ломал старые payload.
