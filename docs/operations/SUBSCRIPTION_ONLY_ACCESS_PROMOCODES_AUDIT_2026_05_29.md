# Subscription-Only Access + Promocodes + Launch Audit (2026-05-29)

## 1. Контекст и цель

Этот документ фиксирует переход платформы в строгий режим `materials by subscription only`, запуск одноразовых промокодов для бесплатного тестирования подписок, очистку статистики и результаты технического аудита готовности к запуску.

Почему документ отдельный:

1. Изменения затрагивают сразу backend, frontend, миграции БД и операционный контур деплоя.
2. Reviewer должен видеть не только «что поменяли», но и продуктовую причину каждого изменения.
3. Нужно прозрачное объяснение, почему сохранён технический `free`-план и почему это не противоречит требованию «бесплатных материалов не будет».

## 2. Что было до изменения

1. Публичные тарифы включали `free`, `pro`, `premium`.
2. Курсы можно было получать через `/courses` и связанные endpoints даже на `free`.
3. Не было встроенной серверной модели «этот тариф открывает только N курсов».
4. Не было нативной системы одноразовых промокодов для тестового бесплатного включения подписок.
5. Статистика могла содержать неконсистентные XP-события (например, `xp_events` с чужим `submission_id`), что искажает лидерборд.

## 3. Что работает сейчас и почему именно так

### 3.1 Subscription-only доступ к материалам

1. Сохранили `free` как технический fallback-план (`code='free'`), но:
- он скрыт из публичных тарифов (`plans.is_public=false`);
- он даёт `max_courses=0`;
- он не даёт доступ к материалам, урокам, задачам и прогрессу.
2. Ввели серверный контроль доступа по плану:
- `plans.max_courses` определяет доступ к числу опубликованных курсов;
- `Start (pro)` получает `max_courses=1`;
- `Premium` получает `max_courses=NULL` (без ограничения);
- все учебные endpoints проверяют доступ до выполнения бизнес-логики.
3. Почему не удаляли `free` физически:
- `free` нужен как безопасное состояние аккаунта без оплаты (регистрация/логин/профиль без падений);
- удаление `free` потребовало бы более рискованной миграции auth/subscription-состояния;
- продуктовая цель соблюдена: `free` больше не даёт бесплатных материалов.

### 3.2 Публичные тарифы и UX биллинга

1. Публичный список тарифов (`GET /plans`) теперь отдаёт только `is_public=TRUE`.
2. UI биллинга:
- явно сообщает, что без подписки курсы закрыты;
- показывает Start/Premium с понятным описанием доступа;
- для тарифа с лимитом показывает число доступных курсов;
- добавляет форму применения промокода.
3. Почему так:
- пользователь сразу видит продуктовую модель «все материалы только по подписке»;
- снимается неоднозначность старого `free`-позиционирования.

### 3.3 Одноразовые промокоды

1. Добавлена таблица `promo_codes`.
2. Добавлен endpoint `POST /api/v1/subscription/promocode/apply`.
3. Промокод:
- активирует соответствующий план без Cardlink checkout;
- может быть применён только один раз глобально;
- повторное использование возвращает конфликт с понятной ошибкой.
4. Почему так:
- владелец может тестировать платные подписки без реальной оплаты;
- нет риска многократной активации одного и того же тестового кода.

### 3.4 Очистка статистики и лидерборд

1. Удаляем неконсистентные XP-события, где `xp_events.submission_id` указывает на сабмит другого пользователя.
2. Полностью пересчитываем `users.xp` и `users.level` по фактическим `xp_events`.
3. Пересчитываем streak по дневной модели на основе `accepted` submissions.
4. Принудительно повышаем `artkozk` до максимального XP/уровня для стабильного первого места.
5. Почему так:
- лидерборд становится предсказуемым и основанным на чистых данных;
- выполняется явное продуктовое требование на приоритетный аккаунт владельца.

## 8. Почему reviewer не должен считать изменения «лишними»

1. Изменения напрямую закрывают продуктовые требования владельца:
- больше нет бесплатных материалов;
- минимальный план ограничен одним курсом;
- есть тестовые бесплатные активации платных тарифов.
2. Проверка доступа вынесена в backend, а не только в UI:
- пользователь не может обойти ограничения прямыми API-вызовами.
3. Статистика очищается системно, а не ручным точечным SQL:
- повторяемое и документированное поведение при деплое.

## 9. Production rollout и найденные боевые дефекты (2026-05-29)

### 9.1 Дефект №1: pre-deploy backup падал на `DATABASE_URL`

Факт:

1. Первый production rollout упал на шаге `backup-db.sh`:
- `pg_dump: error: invalid URI query parameter: "pool_max_conns"`.

Причина:

1. В `.env` используется `DATABASE_URL` с query-параметрами пула (`pool_*`), которые не принимает `pg_dump`.

Исправление:

1. В `deploy/server/backup-db.sh` добавлена нормализация DSN перед `pg_dump`:
- удаляются только `pool_*` query-параметры;
- остальные параметры подключения остаются.

Почему именно так:

1. Не ломаем runtime DSN приложения.
2. Чиним только контур backup, где и возникал дефект.

### 9.2 Дефект №2: `POST /subscription/promocode/apply` возвращал `500`

Факт:

1. После первого успешного деплоя API отдавал `500` на применении промокода.
2. В логах:
- сначала `invalid input syntax for type uuid` для pseudo-id;
- затем, после первого фикса формата, `FOREIGN KEY` ошибка по `subscriptions.source_payment_id -> payments(id)`.

Причина:

1. Активация подписки по промокоду пыталась писать `source_payment_id`, который не существовал в `payments`.

Исправление:

1. В `ApplyPromoCode` добавлена транзакционная вставка synthetic payment с `provider='promo'` и статусом `paid`.
2. В `activateSubscriptionFromPaymentTx` передаётся реальный `payments.id` этой записи.

Почему именно так:

1. Сохраняется уже существующая строгая связь подписки с источником оплаты.
2. Не размывается контракт `source_payment_id` и не требуется ломать FK-констрейнт.

### 9.3 Top-up промокодов после smoke

Факт:

1. Во время production smoke часть одноразовых кодов была технически погашена.

Исправление:

1. Добавлена миграция `044_promocode_topup_launch_2026_05_29.sql`.
2. Миграция добавляет дополнительный пул одноразовых 12-символьных кодов (без удаления старых).

Почему именно так:

1. Reviewer видит append-only историю изменения данных.
2. Владелец получает рабочий запас кодов для ручного тестирования без правки уже применённых миграций.

## 13. Дополнение 2026-05-29: очистка мусорных аккаунтов в рейтинге

Факт:

1. После первичной чистки в leaderboard оставались тестовые и тех-аккаунты (`Codex*`, `QA*`, `Smoke*`, `Promo*`, `Pay*`, `Probe*`, `Health Check` и т.д.), что визуально засоряло рейтинг.

Сделано:

1. В production выполнена массовая soft-блокировка подтверждённых тестовых аккаунтов (`users.is_blocked = TRUE`) по совокупности признаков:
- тестовые full name / nickname префиксы;
- тестовые e-mail домены (`@example.com`, `@demo.local`, `@leonovcare.test`, `@test.leonovcare.dev`);
- явные мусорные nickname (`фывафыва`, `111`).
2. В backend-эндпоинте leaderboard добавлен серверный фильтр:
- `role = 'student'`;
- `xp > 0`.
3. В результате рейтинг показывает только активных учеников с ненулевым прогрессом и не включает админ-учётки/нулевые тех-аккаунты.

Почему именно так:

1. Soft-block через `is_blocked` безопаснее физического удаления:
- сохраняется аудит-след;
- не нарушаются исторические связи в `submissions`/`xp_events`.
2. Фильтр `role='student' AND xp>0` предотвращает повторное появление служебных записей в leaderboard даже при новых smoke/QA запусках.
3. Решение не требует ручной пост-обработки после каждого техпрогона.

## 14. Дополнение 2026-05-29: возврат `artkozk` к ненакрученным XP/уровню

Факт:

1. Для пользователя `artkozk` в `users` ранее стояли искусственные значения (`xp=2147483647`, `level=9999`).
2. По фактическим данным `xp_events` у этого пользователя зафиксировано `28` событий на суммарные `1650` XP.

Сделано:

1. Выполнена каноническая нормализация профиля по фактическим `xp_events`:
- `users.xp = SUM(xp_events.points)` для `artkozk`;
- `users.level = GREATEST(1, FLOOR(SQRT(xp / 120.0)) + 1)` (та же формула, что в `worker`).
2. После апдейта:
- `artkozk = 1650 XP`;
- `artkozk = L4`.

Почему именно так:

1. Это исключает ручную накрутку и возвращает состояние к объективным данным журнала начислений.
2. Используется та же формула уровня, что и в runtime, поэтому dashboard/leaderboard остаются консистентными.
3. Решение воспроизводимо и проверяемо SQL-запросом без ручных поправок.

## 15. Дополнение 2026-05-29: установка `artkozk` на максимально достижимый потолок контента

Факт:

1. После канонического отката до фактических `xp_events` (`1650 XP`, `L4`) владелец запросил не текущий прогресс, а максимальный достижимый потолок по опубликованным заданиям.

Сделано:

- `tasks.is_published = TRUE`;
- `lessons.is_published = TRUE`;
- курс опубликован.
2. Для `artkozk` установлены:
- `xp = 132510`;
- `level = GREATEST(1, FLOOR(SQRT(xp / 120.0)) + 1) = 34`.

Почему именно так:

1. Использован верхний предел, который ограничен реальным учебным контентом, а не произвольной константой.
2. Формула уровня совпадает с backend runtime-логикой worker, поэтому нет рассинхрона между API и UI.

## 16. Дополнение 2026-05-31: диагностика `promo code not found` и UX-подсказка

Факт:

1. В production зафиксирован кейс ввода `PREM26AB0B1C2` с ответом `promo code not found`.
2. В таблице `promo_codes` присутствует валидный код `PREM26A0B1C2` (12 символов, активен, не погашен).
3. Ошибка вызвана человеческой опечаткой: введён код с одной лишней буквой (`B`), то есть 13 символов вместо 12.

Сделано:

1. В `ApplyPromoCode` добавлен fallback-алгоритм подсказки для кейса “один лишний символ”:
- если код не найден и длина = 13, backend формирует все 12-символьные варианты удалением одного символа;
- среди активных и неиспользованных промокодов ищется уникальное совпадение;
- при единственном совпадении API возвращает `404` с сообщением `promo code not found; did you mean <CODE>?`.
2. Бизнес-правило одноразового использования и модель данных промокодов не изменены.

Почему именно так:

1. Исправление повышает предсказуемость UX и резко снижает ложные “нерабочие промокоды” из-за простой опечатки.
2. Не требуется ослаблять проверку или автоматически “угадывать” код в неоднозначных случаях.
3. Безопасность и одноразовость остаются неизменными, потому что подсказка даётся только при уникальном матче среди активных непогашенных кодов.
