# Business Control: миграция production-контура 2026-08-13

## 1. Цель изменения

Business Control переносится со старого узла `85.198.82.221` на выделенный серверный контур `178.234.15.210`. Одновременно удаляется общий nginx Basic Auth пользователя `founders`: после миграции первым экраном должна быть собственная форма входа и регистрации Business Control.

Изменение не затрагивает Minecraft на порту `25565`, панель Proxmox на порту `8006` и другие гостевые системы. Приложение должно работать отдельным процессом за nginx и слушать только loopback `127.0.0.1:8522`.

## 2. Почему общий Basic Auth больше не используется

Первый production-запуск дополнительно защищал приложение общим паролем до появления двух личных аккаунтов. Это создавало второй, не относящийся к приложению экран входа и ухудшало ежедневную работу. Актуальная схема оставляет только штатную авторизацию Business Control:

1. регистрация разрешена серверным allowlist `artkozk,sweetybboy`;
2. пароль каждого пользователя хранится только в виде bcrypt-хеша;
3. сессия находится в HttpOnly cookie с `Secure` и `SameSite=Lax`;
4. nginx не содержит директив `auth_basic` и `auth_basic_user_file`;
5. индексирование по-прежнему запрещено заголовком `X-Robots-Tag`.

Ограничение allowlist не является полноценной системой приглашений: пока `sweetybboy` не зарегистрирован, теоретически существует риск занятия этого логина посторонним посетителем. Поэтому одноразовые приглашения отмечены как приоритетное усиление, но не возвращают постоянный общий пароль перед каждой страницей.

## 3. Перенос данных без потерь

Перед миграцией приложение на старом сервере кратковременно останавливается, затем SQLite создаёт согласованную резервную копию. До удаления старого экземпляра обязательны четыре независимые проверки:

1. `PRAGMA integrity_check` возвращает `ok`;
2. локальный и серверный SHA-256 резервной копии совпадают;
3. на новом сервере присутствуют ожидаемые пользователи и количество карточек;
4. новый HTTPS health-check и вход существующего пользователя работают.

Снимок от 2026-08-13 прошёл проверку целостности. Он содержит пользователя `artkozk` и одну карточку. SHA-256 переносного файла: `8fc88d33500e61e32e86a7757634a12a17d7d26d418434b951c7e43faa6fdd56`.

Резервная копия хранится вне Git и не должна добавляться в репозиторий, потому что содержит пользовательские данные и хеш пароля.

## 4. Целевая схема развёртывания

- публичный адрес: `https://business-control.178-234-15-210.sslip.io/`;
- nginx принимает HTTP/HTTPS и проксирует запросы на `127.0.0.1:8522`;
- systemd запускает отдельного системного пользователя `business-control`;
- SQLite хранится в `/var/lib/business-control/business-control.db`;
- секреты и production env хранятся в `/etc/business-control.env` с mode `0600`;
- локальный backup timer создаёт ежедневные согласованные копии;
- приложение не открывает отдельный публичный порт и не меняет сетевые правила Minecraft или Proxmox.

## 5. Порядок миграции

1. Проверить SSH fingerprint нового сервера и убедиться, что подключение ведёт в предназначенную гостевую ОС, а не на гипервизор.
2. Проверить занятые порты, nginx-конфигурацию и существующие systemd units без удаления чужих файлов.
3. Установить бинарник и units Business Control в отдельные каталоги.
4. Перенести проверенную SQLite-копию с владельцем `business-control:business-control` и mode `0600`.
5. Установить nginx-конфигурацию без Basic Auth, выпустить Let's Encrypt сертификат и включить HTTPS redirect.
6. Проверить health endpoint, заголовки, вход `artkozk`, пользователя и карточку в БД, backup timer и автоматический старт сервиса.
7. Только после успешных проверок остановить и удалить старый экземпляр.

## 6. Удаление со старого сервера

После подтверждённого запуска нового контура удаляются только выделенные артефакты Business Control:

- systemd service и backup timer;
- nginx site и файл общего Basic Auth;
- сертификат старого имени через certbot;
- `/opt/business-control`, `/var/lib/business-control`, `/etc/business-control.env`;
- `/usr/local/sbin/business-control-backup`;
- системный пользователь и группа `business-control`;
- временный файл переноса после проверки нового сервера.

После удаления выполняются `systemctl daemon-reload`, `nginx -t`, повторный поиск файлов по точному имени проекта и проверка отсутствия процессов/портов. Общие nginx-журналы и system journal не очищаются целиком: их удаление уничтожило бы аудит других проектов на общем старом сервере.

## 7. Фактическое состояние на момент подготовки

На 2026-08-13 переносная база готова, актуальная nginx-конфигурация в репозитории больше не содержит Basic Auth, а целевое DNS-имя разрешается в `178.234.15.210`.

Развёртывание и очистка старого узла ещё не считаются завершёнными. TCP-порт `178.234.15.210:2221` принимает соединение, но закрывает его до выдачи SSH banner, поэтому пароль не проверяется. Учётная запись `artkozk@pve` успешно входит в Proxmox API, однако API возвращает пустой список ВМ/контейнеров и не выдаёт `Sys.Audit` для узла. До восстановления SSH или назначения прав на целевую ВМ удаление рабочего старого экземпляра запрещено правилами переноса без потерь.

## 8. Rollback

Пока новый контур не прошёл smoke-проверку, старый systemd-сервис и база остаются рабочими. Если новый запуск не проходит health-check или проверку данных, DNS/имя не переключаются, старый сервис продолжает работу, а диагностика выполняется на новом узле. После окончательной очистки rollback возможен из проверенного transfer backup, который до завершения миграции хранится вне удаляемого сервера.

## 14. Актуальный rollback после очистки

Раздел 8 описывает rollback во время миграции. После решения не переносить тестовую БД и фактического удаления старого экземпляра возврат выполняется повторным развёртыванием бинарника и созданием новой БД. Возвращать прежнюю тестовую учётную запись или карточку не требуется. Рабочие данные, которые появятся на `control.e-rd.ru`, должны восстанавливаться из backups нового сервера; до настройки offsite-копии потеря всего нового узла остаётся известным риском P0.
