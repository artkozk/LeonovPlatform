# Implementation Changelog

## 2026-04-23 — v2.0 (полный MVP платформы)

### Добавлено

1. Backend API на Go/Gin с auth, learning, submissions, billing, admin.
2. PostgreSQL migrations + seed демо-курса.
3. Redis queue + worker для асинхронной проверки решений.
4. Java execution engine с compile/run тестами.
5. XP/уровни/достижения/лидерборд.
6. Cardlink payment контур в режиме готовности к merchant config.
7. Frontend на React/Vite с адаптивным UI.
8. Editor-based flow для решения задач прямо в браузере.
9. Admin analytics + CSV export.
10. Тесты backend/frontend и deployment runbook.

### Почему реализовано именно так

1. Приоритет выбран на полный end-to-end продукт для учеников: от регистрации до решения задач и оплаты.
2. Каркас платежей доведен до рабочего состояния без merchant id, чтобы после выдачи реквизитов включение было моментальным.
3. Демо-курс встроен в seed, чтобы платформа была проверяема сразу после старта.
4. Документация оформлена как эксплуатационный артефакт, чтобы ревью и сопровождение были прозрачными.

## 2026-04-23 — v2.6 (social auth reliability + premium minimal auth style)

### Добавлено/исправлено

1. `GET /auth/oauth/google/start` теперь отдает `clientId` при готовой конфигурации.
2. Frontend auth больше не зависит только от `VITE_GOOGLE_CLIENT_ID`:

3. Соц-кнопки переведены в честные состояния:
- активны только при реальной готовности провайдера;
- при неготовом провайдере показывается статус, а не ложная “рабочая” кнопка.

- светлая строгая карточка, чистая типографика, приглушенные цвета, без “кислотных” эффектов.

### Почему реализовано именно так

1. Устранена причина жалобы “не работает”: UI перестал показывать активный OAuth вход без backend-конфига.
2. Runtime-подхват `clientId` сокращает зависимость от rebuild фронтенда при server-side изменениях.
3. Визуальный стиль приведен к более дорогому и сдержанному виду, соответствующему product-level интерфейсу.

## 2026-04-23 — v2.8 (submission polling fix + RU error localization)

### Добавлено/исправлено

1. Исправлен backend-дефект в `GET /submissions/:submissionID`:
- nullable поля `compile_output`, `run_log`, `feedback` теперь читаются через `sql.NullString`;
- при `pgx.ErrNoRows` возвращается `submission not found`, при остальных ошибках — корректный `500`, а не ложный `404`.
2. Исправлен пользовательский сценарий с ошибкой `submission not found` сразу после отправки решения:
- queued submission больше не ломается на чтении `NULL` полей.
3. На странице задачи добавлена русская локализация типовых API ошибок и статусов проверки:
- перевод ошибок отправки/лимитов/доступа;
- перевод статусов `queued/accepted/wrong_answer/compile_error/runtime_error/time_limit`;
- перевод англоязычных UI-подписей (`Difficulty`, `Score`, `Compile output`, `Run log`).

### Почему реализовано именно так

1. В корне проблемы был не “пропавший submission”, а техническая ошибка чтения nullable колонок, поэтому фикс сделан в backend-слое данных.
2. Локализация сделана в UI-слое как безопасный адаптер к текущему API-контракту, без ломки существующих backend-интеграций.
3. Разделение на data-fix + UX-fix одновременно закрывает и техническую, и продуктовую часть жалобы пользователя.

## 2026-04-29 — v2.36 (submission queue stuck fix in worker SQL)

### Добавлено/исправлено

- submission оставался `queued`, но job в очередь повторно уже не возвращался.

### Почему реализовано именно так

1. Проблема находилась в SQL-слое воркера, а не в UI polling или в judge runtime, поэтому точечный фикс сделан в запросах worker-контура.
2. Явная квалификация `s.id` обязательна для стабильности при join-запросах и исключает двусмысленность при любой эволюции схемы.
3. Явное приведение `$2::text` фиксирует типовую неопределенность PostgreSQL и делает retry-механику детерминированной при любых текстовых сообщениях об ошибках.

3. Значение `swappiness=10` снижает вероятность агрессивного вытеснения рабочей памяти в swap.

3. Кликабельность списка проверок закрывает UX-разрыв: пользователь сразу переходит к месту исправления и к нужной отправке, вместо ручного поиска задачи.

## 2026-05-08 — Frontend materials cache persistence (ускорение cold-start загрузки обучения)

### Симптом до изменения

1. На странице `Обучение` и при открытии уроков повторно загружались те же учебные материалы после refresh вкладки.

3. Отдельный TTL для материалов отделяет почти статичный контент курса от часто меняющихся operational-данных.

## 2026-05-13 — Protected domain incident response (`leonovcare.ru`) + deploy guard

### Симптомы и критичность

1. Внешний домен `leonovcare.ru` оказался направлен на LeonovCarePlatform (контур разработки), хотя этот домен занят другим сайтом.
2. Это критичный production-инцидент, потому что нарушается публичная доступность основного сайта владельца домена.

### Что сделано

1. На сервере выполнен rollback nginx-конфига `leonovcare.ru` на исторически корректную версию.
2. В `deploy/server/deploy.sh` усилен preflight `enforce_domain_lock`:
- деплой падает, если защищённый домен указывает на `frontend/dist` текущего проекта;
- деплой падает, если в конфиге есть прокси на `127.0.0.1:8510` или `127.0.0.1:8511`;
- при отсутствии файла защищённого домена deploy блокируется (fail-closed), а не пропускается.
3. Добавлен отдельный подробный ops-док:
- `docs/operations/DOMAIN_PROTECTION_LEONOVCARE_RU_2026_05_13.md`.
4. Обновлены runbook-документы:
- `DEPLOYMENT.md` (раздел 20);
- `docs/operations/DEPLOYMENT_RUNBOOK.md` (раздел 31);
- `README.md` (актуализация 2026-05-13);
- `docs/operations/SERVER_FIXES_2026_05_11.md` (append-only уточнение текущего статуса домена).

### Как работает сейчас

1. Канонический deploy-flow перед сборкой проверяет защищённый домен и не позволяет развернуть LeonovCarePlatform при нарушении доменной политики.
2. Домен `leonovcare.ru` остаётся закреплён за прежним сайтом и не участвует в контуре LeonovCarePlatform.

### Почему сделано именно так

1. Процессного запрета (только текстовой инструкции) недостаточно для защиты от повторной ошибки при ручных инфраструктурных изменениях.
2. Технический guard на раннем этапе deploy даёт самый дешёвый и быстрый stop-сигнал до build/migration/restart.
3. Fail-closed выбран намеренно: неизвестное состояние защищённого домена не должно считаться безопасным по умолчанию.
