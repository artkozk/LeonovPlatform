# PROMOCODE_COLLISION_IDEMPOTENCY_FIX_2026_06_16

## Кратко

22 июня 2026 в проде снова упало применение промокодов с `500` и `SQLSTATE 42P10`. Причина — старый бинарник backend всё ещё использовал `INSERT ... ON CONFLICT` для `provider_payment_id`, но в этой схеме нет нужной уникальной/исключающей привязки.

## Что именно было сломано

1. В `/api/v1/subscription/promocode/apply` для активации кода выполнялся путь вставки платежа с конфликтным апдейтом для пары `(provider, provider_payment_id)`.
2. В актуальной схеме это приводило к ошибке `42P10` (`there is no unique or exclusion constraint matching the ON CONFLICT specification`) и ответу `500 internal server error`.
3. Это делало фронт-ошибку `bad request`/`500` даже для технически валидного, ещё неиспользованного кода.

## Что исправлено

В `backend/internal/app/handlers_billing.go` (`ApplyPromoCode`) внесены следующие изменения:

1. Перед вставкой теперь выполняется явная проверка существующего платежа:
   - `SELECT id,user_id,created_at FROM payments
      WHERE provider='promo' AND provider_payment_id='PROMO-'||promoID`.
2. Если запись уже есть:
   - при необходимости синхронизируются поля `promo_codes.redeemed_by_user_id / redeemed_at`;
   - возвращается `409` (`promo code already redeemed`) или `409 promo code already redeemed by this account`.
3. Если записи нет — создаётся новый платеж без конфликтного `ON CONFLICT` у вставки:
   - `INSERT INTO payments ... RETURNING id`.
4. Оставлен безопасный фоллбек на редкий race `23505` (для конкурентного двойного запроса):
   - повторно читается платеж по `provider_payment_id` и возвращается `409`.

## Почему так

1. Это устраняет ошибку уровня SQL-конфигурации (`42P10`) без изменения бизнес-правила «промокод одноразовый».
2. Поведение становится идемпотентным: второй запрос на тот же код больше не падает 500, а явно сообщает занятость.
3. Синхронизация `promo_codes` в месте активации защищает от расхождений между `promo_codes` и `payments`, которые уже могли накопиться в прошлых релизах.

## Что ещё ломалось вместе с этим

- На момент проверки видно, что **стартовый релиз все равно возвращал старый код** с `ON CONFLICT` (логи `/root/.pm2/logs/leonovcare-api-2-out-*.log`), поэтому нужно было не только поправить код, но и гарантировать его выкат на актуальный `current`.

## Как проверялось на проде

1. Логи после выкатки:
   - `500` по `POST /api/v1/subscription/promocode/apply` отсутствуют для валидных кодов.
2. Сырые ручные проверки:
   - `POST /api/v1/subscription/promocode/apply` с пустым `redeemed_at`:
     - первый запрос: `200 {"status":"promo_applied",...}`;
     - второй запрос тем же кодом: `409`.
3. Админские и базовые ручные проверки API:
   - `POST /api/v1/auth/login` работает как для `admin`, так и для `admin@platform.local` (пароль `123123123` после синка пароля).
4. В БД валидировано, что неприменённый код не падает в `409`, применённый — переходит в `409`.

## Дополнительные заметки

- На проде дополнительно сохранена история восстановления промокодов (`PROMOCODE_REACTIVATION_2026_06_16.md`) — это отдельный уровень поддержки состояния, не замена кода endpoint’а.
