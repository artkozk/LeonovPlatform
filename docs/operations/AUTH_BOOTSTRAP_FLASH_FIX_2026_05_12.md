# Auth Bootstrap Flash Fix — 2026-05-12

> историю. Новые правки добавляются вниз с датой и автором.

## 1. Контекст

1. Дата возникновения отчёта: 2026-05-12.
2. Автор: Claude (по запросу пользователя через Claude Code).
3. Симптом, описанный пользователем: «при открытии платформы она на
   секунду показывает окно регистрации, даже если я залогинен. Такого
   быть не должно».
4. Затронутая область: SPA-фронтенд (`frontend/src`), модуль auth.

## 2. Корневая причина бага

1. На холодной загрузке SPA исполняется такая последовательность:
   1. `main.tsx` рендерит компонент `<Bootstrap>`.
   2. `<Bootstrap>` ставит `useEffect(() => { void bootstrap(); }, [])`.
      Этот эффект исполняется **после** первого рендера дерева.
   3. Первый рендер дочернего `<App>` идёт с начальным состоянием
      auth-store: `user = null`.
   4. `<App>` рендерит `<Routes>` → `<ShellPage>` → `<ProtectedRoute>`.
   5. `<ProtectedRoute>` смотрит `user` — он равен `null` — и возвращает
      `<Navigate to="/auth" replace />`. React Router переходит на
      `/auth`, монтирует `<AuthPage>`. Браузер успевает отрисовать форму.
   6. Только после этого исполняется `useEffect` из шага 1.2, делает
      `GET /me`, получает профиль, выставляет `user` в store.
   7. `useEffect` внутри `<AuthPage>` видит, что `user !== null`, и
      вызывает `navigate("/dashboard")`.
2. Итог: пользователь, у которого реально валидный токен в
   `localStorage`, видит форму логина на 100–300 мс, после чего его
   "выкидывает" на дашборд. Это и есть наблюдаемая "вспышка".

## 3. Почему ловить это через `loading`-флаг было нельзя

1. В store был флаг `loading: boolean`, но он выставлялся **внутри**
   `bootstrap()` — то есть только после того, как `useEffect` уже
   успел исполниться. На первом рендере он был `false`, и `<ProtectedRoute>`
   не имел способа узнать, что bootstrap ещё впереди.
2. Менять `loading` синхронно при создании store нельзя: store создаётся
   на этапе модульной инициализации, ещё до того, как мы вообще знаем,
   будет ли запрошен `bootstrap()` (для рендера на /auth-маршруте без
   токена он не нужен).

## 4. Решение

1. В `frontend/src/store/auth.ts` добавлено новое поле `bootstrapped:
   boolean` в `AuthStore`.
2. Инициализация поля выполняется один раз при создании store:
   - Если `localStorage` **не содержит** access-токена — значит, юзер
     заведомо разлогинен, ждать нечего: `bootstrapped: true`.
   - Если access-токен **есть** — значит, нужно ждать ответа `/me`:
     `bootstrapped: false`. Переключится в `true` после того, как
     `bootstrap()` доведёт первый цикл проверки до конца (успех/неуспех
     неважен — важно, что мы выяснили статус сессии).
3. `bootstrap()` дополнен таким образом, что во всех ветках
   (нет токена; ответ /me пришёл; ответ /me был null; logout случился
   во время await; брошено исключение) финально выставляется
   `bootstrapped: true`.
4. `login()` и `register()` тоже выставляют `bootstrapped: true` на
   успехе. Если они вообще успели отработать — мы заведомо знаем
   статус сессии.
5. `logout()` оставляет `bootstrapped: true`: после явного выхода мы
   не "забыли" про юзера, мы знаем, что он разлогинен.
6. `frontend/src/components/ProtectedRoute.tsx`:
   - Если `bootstrapped === false` — компонент возвращает `null`
     (пустой плейсхолдер) вместо редиректа. Это блокирует "вспышку",
     но визуально на дашборде это пустой кадр на ~100 мс, а не форма
     чужого экрана.
   - Когда `bootstrapped === true` — поведение прежнее: есть `user` —
     показываем содержимое, нет — `<Navigate to="/auth" replace />`.
7. `frontend/src/pages/AuthPage.tsx`: симметрично — пока
   `bootstrapped === false`, возвращаем `null`. Это закрывает зеркальный
   сценарий: юзер с валидным токеном открыл `/auth` напрямую (например,
   из закладки), и без этой защиты успел бы увидеть форму логина до
   того, как сработает редирект на `/dashboard`.

## 5. Почему именно так, а не иначе

1. Альтернатива A — рендерить общий <Suspense fallback="лоадер"> с
   подвешенным promise — потребовала бы либо React 19 use(), либо
   ручной интеграции с роутером. Это перебор для такой простой задачи.
2. Альтернатива B — синхронно тащить профиль через `localStorage`,
   например, кэшировать его рядом с токеном — даёт SSR-подобный
   опыт, но даёт и реальный риск: профиль в localStorage может быть
   устаревшим (см. предыдущий аудит cross-account leak от 2026-05-12,
   docs/operations/CROSS_ACCOUNT_LEAK_FIX_2026_05_12.md — отсутствует,
   см. вместо него коммит `15eda1c`). Здесь мы сознательно НЕ кэшируем
   профиль, потому что флаг `bootstrapped` сам по себе решает UX,
   не открывая нового вектора утечки.
3. Альтернатива C — поднять `loading` до создания store — нерабоча,
   потому что на маршруте /auth без токена `bootstrap()` вообще не
   нужен, и держать UI в "loading"-состоянии без причины — плохо.
4. Выбранный путь сохраняет инвариант: рендер не зависит от того,
   успел ли отработать `useEffect`. Состояние, доступное на первом
   рендере, уже отражает истину — либо "точно разлогинен", либо "пока
   неизвестно".

## 7. Как проверить вручную после деплоя

1. Залогиниться на платформе. Закрыть вкладку.
2. Открыть `https://leonovcare.ru/` заново.
3. Ожидаемое поведение: на долю секунды может появиться пустой кадр,
   но **форма логина показываться не должна** — сразу появляется
   дашборд.
4. Альтернативная проверка: открыть DevTools → Network → throttle до
   "Slow 3G". Открыть сайт. Форма логина не должна появляться даже
   при медленной сети — будет пустой кадр до тех пор, пока `/me` не
   ответит.
5. Регрессионная проверка: открыть сайт **без** валидного токена в
   localStorage (приватное окно). Поведение должно остаться прежним —
   форма логина показывается сразу.
