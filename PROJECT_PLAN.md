# Leonov Care — Детализированный план реализации проекта

## 1. Назначение документа

Этот документ фиксирует рабочий план реализации проекта **Leonov Care** на основе базового ТЗ (`leonov_care_tz.docx`) и переводит требования в инженерный план: функции, архитектуру, этапы, критерии готовности и риски.

Документ создан как расширение ТЗ и **не заменяет** исходное ТЗ.

## 2. Контекст и исходные вводные

- Тип продукта: образовательная веб-платформа + плагин IntelliJ IDEA.
- Основной сценарий: пользователь проходит урок, решает задачу на Java, отправляет решение на сервер, получает автоматическую проверку и прогресс.
- Монетизация: подписки Free / Pro / Premium.
- Референс по механике: JavaRush.

## 3. Целевой функциональный состав (scope)

### 3.1 Веб-платформа (пользовательская часть)

1. Регистрация и вход:
- email + username + пароль;
- OAuth (Google, GitHub);
- подтверждение email;
- восстановление пароля.

2. Личный кабинет:
- профиль пользователя;
- текущий уровень, XP, серия решений;
- прогресс по курсам/уровням;
- история попыток решения;
- настройки (тема light/dark, язык, уведомления).

3. Система обучения:
- уроки (теория, пример, закрепляющая задача);
- задачи с уровнями сложности 1–10;
- онлайн-редактор кода (Java) с подсветкой;
- запуск проверки решения;
- показ результата по тестам;
- доступ к разбору после исчерпания попыток.

4. Геймификация:
- XP за принятые решения;
- уровни;
- достижения;
- лидерборд.

5. Подписки:
- Free / Pro / Premium;
- ограничения и преимущества по тарифам;
- активация, продление, отмена;
- интеграция ЮKassa (test/live).

### 3.2 Админ-платформа

1. Управление контентом:
- CRUD уроков;
- CRUD задач;
- редактирование Markdown-контента;
- управление тест-кейсами;
- модерация аккаунтов.

2. Операции проверки кода:
- просмотр логов запусков;
- мониторинг очередей;
- просмотр ошибок компиляции/таймаутов.

3. Аналитика:
- активность пользователей;
- конверсия в подписки;
- успешность решения задач;
- экспорт CSV.

### 3.3 Плагин IntelliJ IDEA

1. Авторизация в платформе;
2. Список задач с фильтрами;
3. Просмотр условий прямо в IDE;
4. Создание шаблона проекта под задачу;
5. Отправка решения на сервер;
6. Отображение результата проверки;
7. Синхронизация XP/уровня/ачивок;
8. Локальные черновики;
9. Учет тарифных ограничений.

## 4. Архитектурный план реализации

## 4.1 Бэкенд-сервисы

Рекомендуемое разделение:

1. `api-gateway` (REST API, auth, rate limit, routing).
2. `learning-service` (курсы, уроки, задачи, прогресс).
3. `submission-service` (попытки решения, оркестрация проверки).
4. `runner-service` (запуск кода в Docker sandbox).
5. `billing-service` (подписки, платежи, webhooks ЮKassa).
6. `gamification-service` (XP, уровни, достижения, лидерборд).
7. `analytics-service` (агрегации, отчеты, CSV).
8. `notification-service` (email-уведомления и события).

На старте MVP допускается модульный монолит на Go с внутренними пакетами под эти домены и выносом в отдельные сервисы после стабилизации.

## 4.2 Хранилища

1. PostgreSQL:
- пользователи, роли, тарифы, курсы, уроки, задачи, тесты, попытки, платежи, достижения.

2. Redis:
- кеш пользовательских сессий;
- rate-limiting;
- временные токены подтверждения;
- очереди задач проверки (если выбран Redis-based queue).

3. Локальное файловое хранилище:
- иллюстрации уроков;
- экспортные CSV;
- артефакты логов (при необходимости краткосрочного хранения).

## 4.3 Frontend

1. SPA на React (рекомендуется для ускорения экосистемой).
2. Модульная структура:
- auth;
- learning;
- profile;
- billing;
- leaderboard;
- admin.
3. Общие UI-принципы:
- поддержка light/dark;
- i18n-слой;
- адаптивная сетка.

## 4.4 Плагин IntelliJ

1. Язык: Kotlin.
2. Слои:
- `auth-client`;
- `tasks-client`;
- `submit-client`;
- `ui-toolwindow`;
- `local-draft-storage`.
3. Хранение токена: штатный secure storage IDE.
4. Протокол взаимодействия: REST + JWT.

## 5. Детализация реализации по функциональным блокам

## 5.1 Auth и управление аккаунтом

### Что реализуем

1. Регистрация пользователя.
2. Подтверждение email.
3. Логин/логаут.
4. OAuth вход.
5. Восстановление пароля.

### Как реализуем

1. Таблица `users` + `email_verifications` + `password_resets` + `oauth_accounts`.
2. Хэширование пароля `bcrypt`.
3. JWT access + refresh (короткоживущий access, ротация refresh).
4. Ограничение попыток на `/auth/login` и `/auth/register`.
5. Email-пайплайн через очередь.

### Критерии готовности

1. Подтверждение email обязательно для полного доступа.
2. OAuth-пользователь может привязать/отвязать парольный вход.
3. Все auth-сценарии покрыты интеграционными тестами.

## 5.2 Курсы, уроки, задачи

### Что реализуем

1. Иерархия: курс → модуль → урок → задачи.
2. Формат уроков Markdown + медиа.
3. Задачи с ограничениями и примерами.
4. Попытки решения и история.

### Как реализуем

1. Таблицы `courses`, `modules`, `lessons`, `tasks`, `task_test_cases`, `submissions`.
2. Версионирование контента (минимум `version` и `updated_by` в админке).
3. Рендер Markdown на frontend с безопасной санитизацией.
4. Политика лимитов попыток по тарифу через middleware.

### Критерии готовности

1. Админ создаёт урок и задачу без правки БД вручную.
2. Пользователь видит последовательный контент по уровню.
3. История попыток доступна в профиле.

## 5.3 Проверка кода (Code Execution Engine)

### Что реализуем

1. Проверка Java-кода в sandbox.
2. Таймаут и лимит памяти.
3. Сравнение вывода с эталоном.
4. Возврат детализированного результата.

### Как реализуем

1. `submission-service` кладёт задачу в очередь.
2. `runner-service` поднимает изолированный Docker контейнер.
3. Пайплайн выполнения:
- компиляция;
- запуск на каждом тест-кейсе;
- сбор stdout/stderr/exit-code;
- вычисление verdict.
4. Ограничения:
- CPU/mem лимиты контейнера;
- сетевой доступ внутри контейнера отключен;
- read-only filesystem + temp workspace.
5. Логирование запусков:
- `submission_runs` (статус, время, память, причина ошибки).

### Критерии готовности

1. 99%+ корректности классификации pass/fail на эталонном наборе.
2. Таймауты и OOM корректно маркируются.
3. Нет возможности обращения к внешней сети из sandbox.

## 5.4 Геймификация

### Что реализуем

1. Начисление XP.
2. Формула уровня.
3. Ачивки и триггеры.
4. Лидерборд.

### Как реализуем

1. Таблицы `xp_events`, `user_levels`, `achievements`, `user_achievements`.
2. Event-driven обработка: `submission.accepted` → `gamification-service`.
3. Лидерборд через materialized view + Redis cache.

### Критерии готовности

1. XP начисляется атомарно и без дублей.
2. Ачивки выдаются один раз по выполнению условий.
3. Лидерборд обновляется в заданный SLA (например, до 60 секунд).

## 5.5 Подписки и платежи

### Что реализуем

1. Тарифы Free/Pro/Premium.
2. Ограничения на попытки/контент.
3. Подключение ЮKassa.
4. Webhook-обработка платежного статуса.

### Как реализуем

1. Таблицы `plans`, `subscriptions`, `payments`, `payment_events`.
2. Плановая модель доступа через policy middleware (`feature gates`).
3. Проверка подписи webhook и идемпотентная обработка.
4. Отдельные режимы `test` и `live` через env-конфигурацию.

### Критерии готовности

1. Переключение тарифа изменяет права немедленно или по окончанию периода (по выбранной бизнес-логике).
2. Повторный webhook не ломает состояние.
3. Есть журнал всех платежных событий.

## 5.6 Админка

### Что реализуем

1. CRUD контента.
2. Управление пользователями.
3. Просмотр метрик и экспорт CSV.

### Как реализуем

1. RBAC роли: `admin`, `content_manager`, `support`.
2. Аудит действий админа: `admin_audit_log`.
3. Экспорт через фоновую задачу с ссылкой на скачивание.

### Критерии готовности

1. Любое изменение контента трассируется по пользователю и времени.
2. Экспорт данных работает для заданного диапазона дат.
3. Опасные операции (блокировка/сброс) имеют подтверждение.

## 5.7 Аналитика

### Что реализуем

1. DAU/WAU/MAU.
2. Конверсия в подписку.
3. Воронка обучения.
4. Успешность решений по темам/уровням.

### Как реализуем

1. Сбор доменных событий (`user_registered`, `lesson_opened`, `submission_checked`, `payment_succeeded`).
2. Ежедневные агрегации в таблицы витрин.
3. API для дашборда + CSV экспорт.

### Критерии готовности

1. Метрики воспроизводимы (одинаковый результат при пересчете).
2. Время подготовки дашборда укладывается в SLA.

## 5.8 IntelliJ Plugin

### Что реализуем в V1

1. Логин и хранение токена.
2. Загрузка списка задач.
3. Создание шаблонного проекта.
4. Отправка решения.
5. Вывод результата.

### Как реализуем

1. Tool Window с вкладками: `Tasks`, `Current Task`, `Results`, `Profile`.
2. HTTP-клиент с retry/backoff для нестабильной сети.
3. Локальное хранение черновиков (по `task_id`) в каталоге плагина.
4. Синхронизация прогресса после успешной проверки.

### Критерии готовности

1. Совместимость с IntelliJ 2022.1+.
2. Проверка задачи выполняется без перехода в браузер.
3. При истечении токена есть прозрачный re-login flow.

## 6. API-план (группы эндпоинтов)

1. `POST /auth/register`, `POST /auth/login`, `POST /auth/oauth`, `POST /auth/refresh`, `POST /auth/recover`.
2. `GET /profile`, `PATCH /profile/settings`, `GET /profile/history`.
3. `GET /courses`, `GET /courses/{id}`, `GET /lessons/{id}`, `GET /tasks/{id}`.
4. `POST /tasks/{id}/submit`, `GET /submissions/{id}`, `GET /submissions/{id}/details`.
5. `GET /leaderboard`, `GET /achievements`, `GET /xp`.
6. `GET /plans`, `POST /subscriptions/checkout`, `POST /subscriptions/cancel`, `POST /payments/webhook/yookassa`.
7. `GET /admin/...` для контента/аналитики/модерации.

OpenAPI 3.0 — обязательный артефакт, обновляемый одновременно с изменением API.

## 7. Нефункциональная реализация

## 7.1 Производительность

- Цель: p95 для обычных read-endpoints ≤ 300 ms.
- Проверка кода: асинхронная, отдельный SLA (например, до 5–15 сек в зависимости от очереди).
- Нагрузка: 100 одновременных пользователей как минимум в MVP.

Примечание: в исходном ТЗ указан пункт `Время ответа API: >= 2500 мс`, что выглядит как вероятная опечатка. Для инженерного качества и UX принимаем целевой показатель **не более** 2500 мс, и уточнение фиксируем как открытый вопрос к согласованию.

## 7.2 Безопасность

- OWASP Top-10 практики;
- JWT + ротация refresh;
- TLS на всех внешних соединениях;
- secure headers;
- ограничение попыток auth/submit;
- sandbox hardening;
- сканирование зависимостей в CI.

## 7.3 Соответствие 152-ФЗ

- хранение ПДн на инфраструктуре в РФ;
- публичные документы: политика, оферта, соглашение;
- возрастная маркировка 12+;
- журнал согласий (если требуется юридической моделью).

## 10. Definition of Done (DoD) по системе

Фича считается завершенной, если одновременно выполнено:

1. Реализован backend + frontend/плагин сценарий.
2. Обновлена OpenAPI-спецификация.
3. Добавлены/обновлены автотесты.
4. Есть запись в changelog/документации с обоснованием решений.
5. Пройдены линтеры и CI pipeline.
6. Есть демонстрируемый результат в тестовом окружении.

## 11. Реестр рисков и митигаций

1. Риск: нестабильность sandbox при пиковых отправках.
- Митигация: очередь задач + ограничение конкурентных раннеров + алерты.

2. Риск: ошибочная тарификация при дубле webhook.
- Митигация: идемпотентные ключи и журнал событий платежа.

3. Риск: расхождение логики веба и плагина.
- Митигация: единый API-контракт, контрактные тесты, общая матрица сценариев.

4. Риск: уязвимости при запуске пользовательского кода.
- Митигация: жесткая изоляция контейнера, запрет сети, лимиты ресурсов, регулярные security-сканы.

5. Риск: неоднозначность метрик производительности в ТЗ.
- Митигация: формализовать SLA в отдельном согласованном документе до релиза.

## 12. Почему архитектурные решения выбраны именно так

1. Асинхронная проверка кода через очередь выбрана, чтобы стабилизировать платформу под нагрузкой и не блокировать API долгими задачами.
2. Docker sandbox выбран для безопасной изоляции пользовательского кода и управляемых ресурсных лимитов.
3. JWT + refresh token выбраны для совместимости веба и плагина IDEA с единым подходом авторизации.
4. PostgreSQL + Redis выбраны как баланс надежного хранения транзакционных данных и высокой скорости для кеша/лимитов.
5. Модульный монолит на старте выбран для скорости MVP, чтобы не перегружать проект преждевременной микросервисной сложностью.
