# Mentor handbook v18

## Принцип сопровождения
Не давай готовое решение до диагностики. Сначала выясни урок, шаг, входные данные, ожидаемый результат, фактический вывод и последнюю ошибку. Цель наставника — вернуть студента к ближайшему уже объяснённому понятию, а не заменить практику.

## Как отвечать без готового кода
1. Попроси студента назвать вход, преобразование и выход.
2. Попроси показать минимальный фрагмент, который воспроизводит ошибку.
3. Дай вопрос по одному правилу: тип, отступ, сортировка, статус, транзакция, состояние объекта.
4. Если две попытки не помогли, покажи маленький пример на других данных.
5. Полное решение не отправляй до разбора причины ошибки.

## Типовые ошибки по модулям
### Модуль 1
Лишний stdout, неправильный тип после input, преждевременное использование будущих тем, IndexError, забытый return, грязное Git-состояние.

### Модуль 2
Класс без инварианта, dataclass с общим mutable default, Protocol без структурной совместимости, async без await, pytest без edge case, mock вместо проверки поведения.

### Модуль 3
SQL без ORDER BY, WHERE после GROUP BY, COUNT(column) вместо COUNT(*), потеря строк в LEFT JOIN, rollback не проверен, индекс создан не под фильтр.

### Модуль 4
Body/checker mismatch, 422 из-за Pydantic, 404 вместо HTTPException, response_model скрывает/не скрывает поле, session не закрывается, TestClient не проверяет negative case.

### Модуль 5
AI-ответ без структуры, отсутствие no-answer в RAG, sources не связаны с answer, секрет попал в diff, deploy без rollback, финальный gate сдаётся набором файлов без критерия pass/fail.

## Жалобы на скрытые проверки
Проверь публичный пример, формат вывода, пустые значения, неверные типы, отсутствие сортировки, SQL injection, 401/403/404/422, грязное Git-дерево, отсутствие env/healthcheck. Если hidden case действительно противоречит условию, эскалируй в QA с id шага, входом и ожидаемым поведением.

## Проверка финального проекта
Каждый gate проверяй отдельно: ТЗ, user stories, ERD, API contract, Git workflow, FastAPI structure, SQLAlchemy, Alembic, Auth, CRUD, Tests, Docker, CI/CD, AI integration, logging, README, deploy, defense. Не принимай gate, если нет воспроизводимой команды или pass/fail критерия.

## Маршруты восстановления
Если студент отстал на 1 неделю: пройти summary и 3 практики последнего урока. Если отстал на 2 недели: вернуться к последнему экзамену и закрыть только blockers. Если отстал больше: наставник собирает индивидуальный план по prerequisite_matrix.csv.

## Эскалация
Эскалируй платформенной команде: конфликт body/checker, битый текст, неработающий fixture, некорректный hidden test, IDE-плагин не видит файл, массовая ошибка импорта. Эскалируй методисту: теория не объясняет термин, задача требует будущие знания, проектный gate не имеет критерия сдачи.

## Обновление 2026-05-05: FastAPI ladder
Если студент застрял в первых FastAPI-уроках, не переводите его сразу к базе, auth или Docker. Проверьте по порядку: приложение создаётся, endpoint объявлен, метод совпадает с условием, путь совпадает с проверкой, возвращаемый JSON имеет нужные ключи, статус ответа совпадает с заданием.
Такой порядок нужен, чтобы ревьюер видел педагогическую причину ограничения: ранние уроки закрепляют только один новый навык за раз, а не смешивают HTTP, модели, ошибки и инфраструктуру.

## SEMANTIC_ALIGNMENT_2026_05_05: как проверять исправленные уроки

При жалобе студента сначала сравни тему урока с задачей. Если урок про pathlib, в задаче должны быть `Path`, чтение или запись файла, директории или `tmp_path`. Если урок про mypy, ищи type hints, `Optional`, `TypedDict` или `Protocol`. Если урок про FastAPI healthcheck, не веди студента к auth или CRUD: проверяются только health/readiness/liveness и зависимость readiness. Такой порядок нужен, чтобы наставник не подсказывал решение из будущей темы и не разрушал педагогическую лестницу.
