# IDE Plugin Spec v18

Документ описывает контракт между учебной платформой и IDE-плагином. Он не является источником импорта курса; источником остаётся `course_import.json`.

## Назначение

IDE-плагин проверяет задания, которые нельзя надёжно проверить простым stdout или SQL-запросом: структуру проекта, файлы, команды, Git-состояние, Docker, CI/CD, FastAPI-проекты и финальные gates. Проверка должна давать студенту короткую диагностическую ошибку: что не найдено, какая команда упала, какой файл не соответствует ожиданию.

## Базовый формат checker

```json
{
  "type": "ide_plugin",
  "timeout_sec": 30,
  "required_files": ["main.py", "README.md"],
  "required_dirs": ["src"],
  "forbidden_files": [".env", "secrets.json"],
  "commands": [
    {
      "cmd": "python main.py",
      "expect_stdout": "ok\n",
      "expect_stderr": "",
      "timeout_sec": 5
    }
  ],
  "git_checks": {},
  "hidden_checks": []
}
```

## required_files

`required_files` перечисляет файлы, которые должны существовать перед запуском команд. Плагин должен проверять путь относительно корня задания. Если файла нет, команда не запускается: студент получает ошибку `Не найден файл main.py`.

## commands

Каждая команда запускается в sandbox каталоге задания. Поля:

- `cmd`: команда запуска;
- `expect_stdout`: точное ожидаемое содержимое stdout;
- `expect_stderr`: ожидаемый stderr, если он важен;
- `timeout_sec`: лимит на одну команду;
- `exit_code`: ожидаемый код завершения, по умолчанию `0`.

Плагин не должен показывать скрытые команды студенту. Для открытых команд можно показывать команду и фактический вывод.

## Python и pytest

Для Python-проектов плагин проверяет:

- наличие `main.py`, `src/...` или другого файла из задания;
- запуск программы с примером ввода;
- запуск `python -m pytest`, если задание содержит тестовый проект;
- отсутствие лишнего stdout, когда проверяется функция;
- отсутствие секретов и временных файлов.

Если pytest падает, студент видит имя упавшей проверки и краткий diff ожидаемого результата.

## SQL fixtures

SQL-проекты могут требовать файлы схемы и seed-данных. Плагин должен уметь:

- создать временную SQLite-базу;
- применить `schema.sql`;
- применить `seed.sql`;
- выполнить запрос студента;
- сравнить строки в заданном порядке или как множество.

## FastAPI TestClient

FastAPI-проверка должна импортировать приложение через `app_import`, например `app.main:app`, и выполнять HTTP-запросы через TestClient. Проверяются:

- метод и путь;
- статус ответа;
- JSON subset;
- негативные случаи 401, 404, 422;
- отсутствие лишних полей, если это указано в контракте.

## Docker checks

Docker-задания проверяют:

- наличие `Dockerfile`;
- корректный `COPY` и `CMD`;
- успешную сборку образа;
- запуск контейнера;
- проброс порта;
- healthcheck;
- чтение переменных окружения из `.env.example`.

Команды Docker всегда запускаются с timeout. Плагин должен очищать контейнеры после проверки.

## Docker Compose checks

Compose-задания проверяют:

- `docker compose config`;
- сервисы `app`, `db`, `redis`, если они требуются;
- `depends_on`;
- healthcheck;
- volumes;
- networks;
- отсутствие секретов в YAML.

## Git checks

Git-задания проверяют:

- текущую ветку;
- чистое рабочее дерево;
- наличие нужных веток;
- минимальное число коммитов;
- сообщение последнего коммита;
- отсутствие конфликтных маркеров;
- корректное восстановление через reflog, revert, reset или restore.

Плагин не должен выполнять push в реальный remote. Для remote-сценариев используется локальный bare-репозиторий в sandbox.

## CI/CD checks

CI/CD-задания проверяют YAML-файлы GitHub Actions или GitLab CI:

- отдельные jobs `lint`, `test`, `build`, `deploy`;
- запуск тестов;
- сборку Docker image;
- dry-run деплоя;
- условия запуска deploy только из нужной ветки;
- отсутствие секретов в явном виде.

## Deploy dry-run

Deploy-задания не должны менять реальный сервер. Плагин проверяет `deploy.sh --dry-run`, наличие rollback-функции, проверку health endpoint и понятный exit code при ошибке.

## Sandbox и безопасность

Плагин запускает команды только внутри каталога задания. Запрещены обращения к домашней директории, системным SSH-ключам, реальным `.env`, менеджерам паролей и сетевым адресам вне разрешённого списка. Если команда пытается прочитать секрет, проверка останавливается.

## Сообщения студенту

Ошибка должна быть конкретной:

- плохо: `проверка не пройдена`;
- хорошо: `Файл README.md не найден`;
- хорошо: `Команда python main.py вывела лишнюю строку`;
- хорошо: `Ожидался статус 404, получен 200`;
- хорошо: `В README найдено имя .env с секретом, перенеси секреты в переменные окружения`.


## Матрица диагностических сообщений

Плагин должен возвращать студенту ошибку на уровне действия:

- файл не найден: `Создай файл main.py в корне проекта`;
- команда не запустилась: `python main.py завершилась с кодом 1`;
- stdout отличается: `ожидалась строка ok, получена строка OK`;
- stderr не пустой: `программа пишет ошибку, проверь кавычки или импорт`;
- timeout: `команда не завершилась за 5 секунд, проверь бесконечный цикл`;
- HTTP статус не совпал: `ожидался 404 для неизвестной задачи, получен 200`;
- Docker healthcheck не прошёл: `контейнер стартовал, но endpoint /health вернул ошибку`;
- Git дерево грязное: `после задания остались незакоммиченные изменения`.

## Уровни проверки

1. Static: наличие файлов, отсутствие запрещённых файлов, базовый анализ YAML или Dockerfile.
2. Runtime: запуск команды, сравнение stdout/stderr, проверка exit code.
3. Behaviour: HTTP-запросы, pytest, SQL fixtures, Docker healthcheck.
4. Security: поиск секретов, запрет чтения системных путей, запрет реального push/deploy.
5. Review: AI-review по рубрике, если задание требует архитектурного решения.

## Требования к скрытым проверкам

Скрытые проверки не должны противоречить открытому условию. Они проверяют крайние случаи: пустой ввод, неверный тип, отсутствующий файл, неправильную ветку Git, конфликтные маркеры, отсутствие healthcheck, неверный HTTP статус или грязное рабочее дерево.

## Версионирование

Каждый checker считается контрактом. Если меняются required_files, команды или ожидаемый stdout, нужно обновить версию задания в `admin_notes` или миграции, чтобы ревьюер видел причину изменения.
